Жизненный цикл судебного дела

Как scripts/update_cases.py решает: какое дело и в какой момент парсить, как переводить между стадиями и когда отправлять в архив. Один прогон cron = один оборот пайплайна.

first_instance awaiting_appeal appeal cassation_watch cassation_pending cassation awaiting_relink архив

4. Когда вообще запускается прогон

  • Cron-выражение: "45 3 * * mon-fri" в cloudflare-worker/wrangler.toml = 03:45 UTC = 06:45 МСК, пн–пт.
  • Буквенное mon-fri, а не 1-5. Cloudflare Cron Triggers нумерует дни 1=Sun..7=Sat (не как POSIX). Цифровое 1-5 эмпирически срабатывало и в воскресенье — буквенная нотация однозначна.
  • Второй щит — isHoliday() в worker.js. Отсекает сб/вс через getDay() и сверяется с HOLIDAYS_2026 (производственный календарь РФ; обновлять ежегодно).
  • Worker → GitHub API → workflow_dispatch. Если день рабочий, Worker POST'ит в .github/workflows/update_cases.yml с inputs.smart_skip=true.
  • Двойная защита. Внутри Python переменная SKIP_NON_WORKING_DAYS=1 ещё раз проверяет is_russian_working_day(today) и выходит, если что-то проскочило.

6. Как мы НЕ дёргаем суд лишний раз (smart-skip)

Функция should_skip_case() в scripts/update_cases.py. Применяется для стадий first_instance, cassation_watch, appeal, cassation на этапе обновления карточек. На awaiting_* и cassation_pending вообще не вызывается — там парсинг карточек не идёт.

  • Force-parse страховка: если last_checked_at пуст или прошло ≥ 21 дня — всё равно парсим. Защита от потерянных событий. Ветка стоит ПЕРВОЙ и перебивает все остальные, поэтому с 14.08.2026 трек «Иски банка» ставит last_checked_at уже при заведении дела (make_bank_entry): карточку читает сам приём, и без штампа заведённое дело парсилось бы каждым прогоном до самого заседания.
  • Будущее заседание: следующая плановая дата (из events или явного hearing_date) ≥ сегодня → skip с причиной future_hearing(DD.MM.YYYY).
  • Приостановлено: suspended_until ≥ сегодня → skip с причиной suspended_until(...).
  • Оставлено без движения: если последнее событие содержит «оставлено без движения» и прошло < 7 дней с прошлой проверки → skip с причиной suspended_weekly(Xd/7d).

7. Если кассация отменила — что дальше

Ветка cassation_remanded: дело не теряется и не архивируется, оно начинает новый раунд.

  • Распознавание: parse_cassation_card вытаскивает текст определения и classify_cassation_outcome ставит outcome="cassation_remanded" для исходов вида «решение отменить, направить на новое рассмотрение».
  • Переход: advance_case_stage переводит дело в awaiting_relink. Парсинг карточек прекращается — ждём появления дела в нижестоящей инстанции.
  • Re-link: relink_awaiting_relink_first_instance (или link_cases для апел.) при обнаружении карточки в выдаче поиска:
    • копирует текущие блоки first_instance/appeal/cassation в history (снимок раунда);
    • увеличивает round += 1;
    • ставит стадию first_instance (или appeal, если касс. отправила обратно в апел.);
    • заполняет новый блок данными из найденной карточки.
  • Без таймаута. Архив для awaiting_relink не работает — суды иногда долго регистрируют возвращённое дело, и пропустить его дороже, чем хранить «висящую» запись.

8. Ключевые идеи

  • Поиск новых дел идёт всегда — каждый прогон, по всем включённым 20 судам ХМАО, по апел. суду и по 7-му КСОЮ. Это единственный способ заметить впервые поданное (или вернувшееся через кассацию) дело.
  • Парсинг карточки активен только там, где он что-то даёт. На awaiting_appeal, cassation_pending, awaiting_relink на сайт суда вообще не идём — просто ждём сигнала из соседней инстанции.
  • Два «склеивателя» инстанций. link_cases матчит апел. карточку с делом 1-й инст. link_cassation_cases матчит 7kas-карточку с 1-й инст. или создаёт «discovery»-дело, если в реестре такого ещё нет.
  • В архив уходят 3 стадии — first_instance (45 дн без жалобы), cassation_watch (120 дн без касс.), cassation (финальный исход + 30/45 дн). Остальные 4 ждут бессрочно.
  • После cassation_remanded дело не теряется — awaiting_relink ждёт новую карточку, начинается новый round со снимком прошлого в history.
  • migrate_stages в начале прогона идемпотентно догоняет старые записи под текущую модель: если за ночь появилась касс. жалоба, дело уедет в cassation_pending ещё до того, как будут парситься карточки.
