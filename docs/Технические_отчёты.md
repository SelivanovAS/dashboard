# Технические отчёты парсинга и выпуска дайджеста

Контракт выпуска 07.10.2026. Подтверждения публикации на GitHub, переноса в
региональные клоны, установки на VPS и граница проверки первого штатного отчёта
фиксируются отдельно в [отчёте выпуска](Выпуск_технических_отчётов_2026-10-07.md).
Само наличие файлов не подтверждает работу живых служб.

## Подготовленная доработка пересказов

Доработка 10.10.2026 готовится в общей программе отдельно от перехода
территорий. Её наличие в исходниках не означает установку: текущие пакеты
перехода не пересобираются. Выпуск возможен после завершения перехода и
готовности процедуры следующих обновлений, с отдельной проверкой штатного цикла.

Обычный выпуск продолжает уже сохранённые задания пересказа, но больше
не подбирает автоматически старые `raw_act` из всех архивов. Полный пригодный
текст с временной ошибкой модели допускает ограниченный повтор из сохранённого
источника. Недостаточный текст, конфликт реквизитов и исчерпанные попытки
не входят в число активных повторов. Отсутствие пригодного текста **у нас**
не доказывает отсутствие публикации на сайте суда.

Отчёт отдельно показывает результаты текущего выпуска, активные повторы,
недостатки сохранённых источников и записи, требующие проверки. Название
фактической модели, кэш и доказанная причина резерва сохраняются. Историческая
классификация не считается новой попыткой модели. Старые сохранённые отчёты
со счётчиками исходных статусов также читаются без сложения всех записей
в общее «ожидание пересказов».

Готовые результаты и исходники не удаляются. Истечение специального ожидания
документа не стирает `act_summary_needs_source`: обычная проверка впоследствии
может получить полный текст и закончить пересказ без новой новости. Старое
задание не должно снова пометить уже обновлённый полный источник неполным.
При замене источника новое задание сохраняется вместе с отметкой о замене
старого до обращения к модели, чтобы прерывание не потеряло работу.

Для предварительного разбора накопленного используется команда только чтения:

```sh
python scripts/review_act_summaries.py --data-dir /path/to/region-snapshot/data --region hmao
```

Она читает копию одной территории, выводит хеши входных файлов, категории
записей и состояние связанного ожидания документа. Полные тексты и пересказы
в вывод не попадают. Неоднозначные связи не разрешаются выбором первого дела.
Изменившийся во время чтения снимок отклоняется. Команда не обращается к суду,
модели или доставке и не меняет картотеку. Перед разовой обработкой рабочих
данных повторить инвентаризацию по свежему согласованному снимку.

Получение полных исторических текстов — следующий отдельный ограниченный шаг
после установки и проверки этой доработки. Оно дополняет карточки без новостей
и повторных уведомлений. Схема `cases.json`, правила инстанций и ИЛ, частота
поиска и чтения карточек этим изменением не затрагиваются.

## Что получает владелец

Личный Telegram используется для технического результата вместо текста
юридического дайджеста. Дайджест продолжает формироваться для приложения,
а персональные Web Push сохраняют существующие правила отбора событий.
Групповой Telegram и личный технический канал различаются явно: выключение
текста дайджеста не должно выключать аварийные сообщения.

С 13.10.2026 личное сообщение содержит пять блоков: итог сбора, карточки по
инстанциям, результат (новые дела, изменения, акты, ИЛ), проблемы при их наличии,
капча и пересказы. Блоков доставки и дальнейших действий в сообщении нет.
Сохраняются полный знаменатель, период счётчиков, результат капчи за день,
фактическая модель, кэш и причина резерва. Причины последней попытки явно
отделены от суточной полноты. Пересекающиеся категории не складываются.

Полный HTML/JSON остаётся в артефакте запуска по ссылке «Подробный отчёт»;
сбор сведений о публикации и доставке сохраняется для диагностики. Изменение
формата само по себе не отправляет сообщения и не меняет расписание.

Один подробный отчёт относится к конкретному выпуску и территории. Он показывает:

- дату снимка, регион и идентификатор запуска;
- прочитанные за день карточки относительно полного плана, отдельно по инстанциям;
- состояние источников поиска, причины непрочтения, очереди и предупреждения;
- количество событий выпуска и результат подготовки пересказов актов;
- фактическую модель каждого готового пересказа, кэш, переключения провайдера
  и подтверждённые причины переключений или неуспеха;
- отдельно сборку дайджеста, публикацию данных, проверку сайта и попытки Web Push;
- ссылки на приложение и запуск с подробным отчётом.

HTTP 200 не считается прочитанной карточкой. Нулевая выдача, ошибка поиска и
источник, который сегодня не проверяли, различаются. Недоступные карточки
остаются в запланированном знаменателе. Отчёт не добавляет текст дел, токены,
идентификаторы подписок и адреса push-сервисов.

## Что означает результат доставки

| Этап | Достаточное подтверждение | Чего оно не подтверждает |
|---|---|---|
| Прогон завершён | Подтверждённое завершение и публикация своего региона; одна свежая запись здоровья недостаточна | Полное чтение всех источников |
| Данные опубликованы | Успешная штатная публикация Git | Готовность страницы приложения |
| Выпуск передан GitHub | Доставочный marker принят remote | Завершение replay или рассылки |
| Дайджест собран | Сформирован результат конкретного replay | Его доступность на Pages |
| Сайт подтверждён | Опубликованный файл соответствует ожидаемому содержимому | Показ уведомления на устройстве |
| Web Push принят | Push-сервис принял запрос этой попытки | Получение, показ или прочтение человеком |

`delivered_at` сохраняет прежнее назначение гейта дня. Его нельзя превращать
в доказательство завершения всех внешних этапов. Зелёный статус workflow тоже
недостаточен: штатный путь допускает Web Push без подтверждения Pages после
таймаута, а отдельные операции могут завершиться предупреждением.

Журнал payload сообщений не подменяет журнал исходов отправки. Числа подписок,
попыток, принятых push, ошибок и пропусков считаются отдельно. Одна подписка
соответствует устройству/браузеру, а не обязательно одному человеку.

## Сообщения исполнителя VPS/Mac

Общий CLI — `scripts/technical_report.py ops`. Обработчик
`scripts/court_monitor/technical_report_ops.py` не меняет картотеку, очереди,
контекст дайджеста и доставочные маркеры.

| Событие | Место вызова | Поведение |
|---|---|---|
| `parse-result` | После успешной публикации данных обычного прогона | Молча сохраняет базу сравнения; при подтверждённом ранее сбое сообщает о новом успешном прогоне |
| `retry-result` | После публикации дневной дочитки | Сообщает о существенном приросте, новых событиях/проблемах или восстановлении |
| `failure` | Аварийная ветка оболочки, включая дочитку | Сообщает конкретный сбой; повторы внутри неустранённого состояния подавляются |
| `watchdog` | Независимая служба доставки, до её быстрого выхода | Повторяет неподтверждённый аварийный отчёт и контролирует отсутствие прогона |

Обычные неполные попытки больше не порождают сообщения каждые полчаса.
Предупреждения здоровья сохраняются в итоговом техническом отчёте. Оболочка
не пишет «дайджест отправлен», когда подтверждён только marker GitHub.

Существенный прирост дочитки — пять карточек или пять процентов плана
(меньший порог, минимум одна карточка), достижение полного чтения, новые
события для следующего выпуска либо новая причина непрочтения/предупреждение.
Мелкие приросты копятся относительно последнего сообщённого результата.
Первое подключение без базы сравнения не приписывает всю суточную работу
последней дочитке. В таком сообщении прямо сказано, что повторная рассылка
дайджеста не запускалась.

Контроль отсутствия подтверждённого завершения включается после **10:00 по
Екатеринбургу**. Он использует существующий `court-delivery.timer`; нового
таймера нет. Перед проверкой остаются общий рабочий календарь и окно службы.
Доказательство завершения сохраняет hook после подтверждённой публикации
данных. Один свежий `parse_health.json` недостаточен: парсер записывает его
до окончания всей работы. При первом включении без такого подтверждения
сообщение говорит «завершение не подтверждено», а не утверждает, что запуска
заведомо не было.
Живой владелец общего `.run.lock` определяется по PID и времени старта процесса:
занятый клон не объявляется забытым. Зависший живой процесс этим контролем
не диагностируется. Полная остановка VPS или самой службы доставки также
не может быть обнаружена локальным контролем на том же VPS.

Отчёт использует прежний файл `~/.config/court-monitor/telegram` как данные,
не как исполняемый shell-файл. Состояние находится только в
`ops/mac-local-run/.runtime/technical_report_ops.<регион>.json` и защищается
отдельным lock отчёта. Парсерный lock, delivery journal и parse journal не
изменяются. Дедуп подтверждается после положительного ответа Telegram API;
неуспешная попытка не выдаётся за отправленную. Отказ отчётности не откатывает
успешную публикацию и не запрещает следующую попытку штатной доставки.
После подтверждённого восстановления такой же новый сбой начинает отдельное
состояние и снова уведомляет. Неотправленный старый сбой снимается, когда
подтверждён новый успешный прогон; неотправленное сообщение о восстановлении
повторяет служба доставки, пока не появился новый сбой.

## Проверка и граница выпуска

Тесты используют временные клоны и заглушённый Telegram/Git. Они проверяют
сохранность контекста и транзакций, порядок «публикация → отчёт», молчание
`--check`, рабочий календарь, дневной дедуп, повтор после ошибки Telegram,
восстановление, независимый контроль без запуска парсера и живые lock.

Перед фактическим выпуском код проверяется в каждом региональном checkout;
территориальные данные, `REGION`, настройки Workers и расписания сохраняются.
Подтверждение первого обычного отчёта, публикации Pages и принятия Web Push
проверяется отдельно после разрешённого переноса кода. Локальные тесты этого
не доказывают.

## Настройки и сохранённые результаты

`TELEGRAM_DIGEST_MODE=technical` заменяет личный текст техническим отчётом;
`digest` сохраняет явно выбранную отправку текста. Без override личный канал
определяется совпадением с `TELEGRAM_CHAT_ID_PERSONAL` или положительным chat ID.
В workflows группа выбирается прежней галкой `to_group`; финальный технический
отчёт адресуется личному `TELEGRAM_CHAT_ID_TEST` независимо от этой галки.

`TECHNICAL_REPORT_PATH` задаёт временный JSON одного запуска. Файл проверяется
по региону, ID и попытке Actions; его очищают до запуска. `DEFER_TECHNICAL_REPORT=1`
передаёт финальную отправку шагу `always()` после публикации и попытки push.
Результаты, включая HTML для чтения, сохраняются артефактом Actions на 7 дней.
Сам CLI отчёта работает без pip-зависимостей; отсутствие CLI при сбое checkout
покрывается отдельным коротким сигналом. Штатный календарный пропуск и тест
без публикации обозначаются как пропуск, а не как авария.

Для ручной проверки `python scripts/technical_report.py` без `--send` выводит
HTML, не отправляя сообщений. При такой проверке задавать временный
`TECHNICAL_REPORT_PATH`. JSON содержит агрегаты и аудит моделей, без актов,
сторон дела, ключей API и адресов подписок. Идентификаторы моделей в JSON
сохраняются полностью; в Telegram известные модели имеют читаемые названия.

Аудит пересказов считает один акт одного суда/инстанции один раз. Повторное
обращение к свежему результату не превращает его в отдельный кэш-пересказ.
Старый кэш без автора показывается как «модель не зафиксирована». Причины
резервов сохраняются вместе с успешным пересказом; в сообщении о кэше явно
сказано, что резерв использовался ранее. Если причина технической ошибки
не известна, отчёт не подменяет её предположением о квоте или таймауте.

Для ручных источников отчёт показывает состав из реестра своего региона.
Свежесть ручных дампов отдельно не проверяется: наличие капчи нельзя выдавать
за доказательство отсутствия уже загруженного дампа. Количества актов и ИЛ
относятся к событиям по делам; число найденных актов входит в число изменений.

## Исправление утренней сводки 13.10.2026

Итог дополнительных карточек сохраняется в `parse_health.technical_card_day`
по полному URL и инстанции, без суммирования пересекающихся причин ИЛ/текста.
Успех сохраняется между слотами; поздняя проверка основной очередью тоже закрывает
остаток. Смена дня или региона очищает агрегат. Если учёт начат посреди дня,
отчёт явно говорит о неполном периоде; старый снимок помечается «последняя попытка».
Причины остатка и задания с конфликтами/недостающими реквизитами показываются
отдельно и не могут сопровождаться выводом «действие не требуется».

Капча показывает сумму сохранённых фактических поисков текущего дня, включая
неудачные попытки до успешной. Checkpoint одного поиска заменяется, а не
прибавляется повторно. Нулевой skip не обнуляет результат. Локальный безопасный
журнал `appeal_captcha_day.json` сохраняет метаданные прерванных поисков;
изображений, ответов и ключей в нём нет. Успешная апелляция ХМАО исключается
из списка ручных источников и в последующих слотах.

Регистрации исков банка входят в новые дела (с отдельным числом), а bare provider
без имени модели не прерывает формирование отчёта. Проверка/перерисовка отчёта
сама по себе не разрешает повторную отправку Telegram или Web Push.

Импорт и парсер используют один owner-lock с PID и временем старта процесса.
Парсер ждёт известного живого владельца до 30 секунд и затем штатно пропускает
занятый слот. Неизвестная блокировка остаётся ошибкой, не удаляется автоматически.
Выпуск требует удерживаемого общего окна, чтобы не смешивать старый mkdir-lock
с новой реализацией; расписания и правила рассылки не меняются.

### Завершённые повторы после смены модели (15.10.2026)

Ключ очереди пересказов учитывает модель. Если новая модель успешно обработала
тот же текст с полностью совпадающими метаданными, старое повторяемое задание
закрывается как `superseded`, со ссылкой `superseded_by` на проверенный результат.
Исходник, реквизиты и история старых попыток сохраняются. Такие записи больше
не учитываются в `retry_pending` и не занимают очередной пакет повторов.

Сверка выполняется перед обычными повторами и после свежего либо кэшированного
успеха. Она не вызывает модель и не создаёт события доставки. Успешный результат
повторно проходит проверку источника и ответа. Другой текст, изменённые метаданные,
повреждённый хеш, отказ модели или конфликт реквизитов не закрывают старую задачу.
Для разового локального ремонта существует `summary_queue.reconcile_pending()`:
вызывать только под штатной блокировкой клона, сохраняя резервную копию очереди
и публикуя только её изменение без маркера доставки. Картотеки, контекст дайджеста,
кэш и журналы отправок эта операция не меняет.

### Источники и реальная возможность дочитки (15.10.2026)

Для неполных источников отчёт отдельно сверяет задачи загрузки с картотекой и
архивами: дочитка назначена, по возрастному лимиту не предусмотрена либо её
назначение требует проверки. Месячный слот за пределом 180 дней не считается
обещанием повторной загрузки. При недоступной или несогласованной описи отчёт
прямо сообщает, что расписание не подтверждено; задания не удаляются.

Прежний годовой номер допускается при проверке заголовка акта только если он
уже присутствует в реквизитах той же официальной карточки. Номера из самого
текста акта не добавляются как алиасы. Суд, УИД, инстанция и полнота источника
проверяются независимо. Разовое восстановление исторически обрезанных текстов
не отменяет возрастные ограничения обычного мониторинга и не создаёт новость:
полный документ сохраняется с происхождением, старое задание остаётся в истории,
а подготовка пересказа продолжается в обычном выпуске без повторной рассылки.
