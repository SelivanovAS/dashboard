# 02. Модель данных

## Что это и зачем

Вся «память» системы — это несколько файлов в папке [`data/`](../../data). Базы
данных нет: дела хранятся в обычных JSON-файлах, лежащих в git-репозитории.
Главный из них — [`data/cases.json`](../../data/cases.json), **единый источник
истины** обо всех делах. Остальные файлы — архивы и служебные снимки (последний
дайджест, кэши, журнал рассылки).

Понимать этот документ важно по двум причинам: (1) фронтенд и бэкенд завязаны на
**имена полей** — переименование без миграции ломает дашборд; (2) разделение на
«горячий» и «холодный» архив объясняет, почему старые дела пропадают из дашборда,
но не из репозитория.

## `cases.json` — активные дела

Верхний уровень:

```json
{
  "version": 1,
  "updated_at": "2026-06-30T03:50:27",   // ISO-8601, момент последней записи
  "cases": [ /* массив объектов-дел */ ]
}
```

Файл UTF-8 **без BOM**. Пишет его `update_cases.py` (`save_json`,
[строка 118](../../scripts/court_monitor/storage.py#L118)); читает фронт (`app.js`) и —
частично, ради сторон дела — Cloudflare Worker (админка подписчиков).

### Объект дела

Поля, общие для всех дел (присутствуют у 100% записей):

| Поле | Тип | Смысл |
|------|-----|-------|
| `id` | string | Идентификатор дела. Обычно = номер дела 1-й инстанции (`2-1234/2026`); для дел, найденных сразу в кассации, — номер кассации. |
| `current_stage` | string | Текущая стадия машины состояний. См. [03](03-жизненный-цикл-дела.md). |
| `plaintiff` | string | Истец. |
| `defendant` | string | Ответчик. |
| `bank_role` | string | Роль банка: `Истец` / `Ответчик` / `Третье лицо`. |
| `initial_bank_role` | string | Роль банка при первом обнаружении дела. Нужна, чтобы в дайджесте показать «было → стало», если роль изменилась. Бэкфиллится в `migrate_stages`. |
| `category` | string | Категория дела (иерархическая, через `→`). |
| `notes` | string | Произвольные заметки (ручной ввод). |
| `first_instance` | object \| null | Блок 1-й инстанции (см. ниже). `null` — пока дело на новом круге ещё не подцепилось. |
| `appeal` | object \| null | Блок апелляции. |

Поля, присутствующие **только у части дел**:

| Поле | Когда есть | Смысл |
|------|-----------|-------|
| `cassation` | дело дошло до кассации | Блок кассации (см. ниже). |
| `discovered_via_cassation` | дело найдено сразу в кассации | `true` — карточки нижестоящих инстанций у нас изначально не было. |
| `round` | дело прошло ≥1 отмену кассацией | Номер круга рассмотрения (`2`, `3`…). Отсутствие = круг 1. |
| `history` | то же | Массив снимков прошлых кругов (см. «Повторные круги»). |
| `cassation_pending_since` | стадия `cassation_pending` | Дата (`YYYY-MM-DD`) перехода в ожидание кассационной карточки. |

### Блок `first_instance`

Заполняется парсером карточки суда 1-й инстанции. Основные поля:

| Поле | Смысл |
|------|-------|
| `case_number` | Номер дела в 1-й инстанции. |
| `court`, `court_domain` | Название суда и его поддомен `*.sudrf.ru`. |
| `judge` | Судья. |
| `filing_date` | Дата поступления (`ДД.ММ.ГГГГ`). |
| `status` | Статус из карточки: `В производстве` / `Решено` / `Возвращено` и т.п. |
| `result` | Текст результата рассмотрения. |
| `last_event`, `event_date` | Последнее процессуальное событие и его дата. |
| `hearing_date`, `hearing_time` | Дата/время заседания. `hearing_date` — **якорь** для тайм-аутов архивации (дата резолютивки). |
| `events` | Массив событий из вкладки «Движение дела» (объекты `{date, text, ...}`). |
| `link` | `case_id\|case_uid` — для сборки URL карточки на сайте суда. |
| `act_published` | `true/false` — выложен ли полный текст акта. |
| `act_date` | Дата публикации мотивировки. |
| `act_text` | Текст судебного акта (когда удалось извлечь). |
| `judicial_uid` | УИД дела — сквозной идентификатор для связки инстанций. |
| `last_checked_at` | Когда парсер последний раз обновлял карточку (для skip-логики). |

Флаги движения по инстанциям (триггеры переходов стадии — см. [03](03-жизненный-цикл-дела.md)):

| Поле | Смысл |
|------|-------|
| `appeal_filed`, `appeal_filed_date` | Подана апелляционная жалоба (видно в карточке 1-й инст.). |
| `sent_to_appeal`, `sent_to_appeal_date` | Дело направлено в апелляционный суд. |
| `cassation_filed`, `cassation_filed_date` | Подана кассационная жалоба (идёт через 1-ю инстанцию). |
| `sent_to_cassation`, `sent_to_cassation_date` | Дело направлено в кассационный суд. |

Служебные флаги «событие уже эмитировано в дайджест» (чтобы не дублировать):
`resolved_emitted`, `motivirovka_emitted`, `accepted_pending_emit`. Плюс
`delo_id`, `srv_num`, `material_number` — параметры для точной сборки URL карточки,
`act_analysis` — кэш LLM-разбора акта.

### Блок `appeal`

Структурно похож на `first_instance`. Отличия:

| Поле | Смысл |
|------|-------|
| `judge_reporter` | Судья-докладчик апелляции (вместо `judge`). |
| `result` | Результат апелляции (оставлено/отменено/изменено). |
| `appellant` | Кто подал апелляционную жалобу. |

Остальные поля (`case_number`, `court`, `filing_date`, `status`, `last_event`,
`event_date`, `hearing_date`, `hearing_time`, `events`, `link`, `act_published`,
`act_date`, `last_checked_at`, `act_analysis`) — по смыслу те же.

### Блок `cassation`

Заполняется из карточки 7-го КСОЮ (`_cassation_card_to_block`,
[строка 450](../../scripts/court_monitor/linking.py#L450)). Наиболее «богатый» блок:

| Поле | Смысл |
|------|-------|
| `case_number` | Внутренний номер дела на 7kas. |
| `cassation_number` | Номер кассационной жалобы. |
| `court`, `court_domain` | Всегда 7-й КСОЮ / `7kas.sudrf.ru`. |
| `judge` | Судья-докладчик кассации. |
| `filing_date` | Дата подачи кассационной жалобы. |
| `fi_decision_date` | Дата решения 1-й инстанции (из карточки кассации). |
| `act_kind`, `category` | Вид акта и категория дела. |
| `judicial_uid` | УИД — связь с нижестоящими инстанциями. |
| `appellant`, `appellant_is_bank`, `appellant_status` | Кассатор, флаг «это банк», его процессуальный статус. |
| `review_result` | Результат рассмотрения (сырой текст). |
| `decision_date` | Дата вынесения кассационного определения. |
| `result_text`, `result_for_appeal` | Текст результата и его влияние на апелляционный акт. |
| `outcome` | **Детерминированный enum исхода** (`cassation_remanded`, `cassation_other`, …). Считается `classify_cassation_outcome`. Управляет переходами стадии. |
| `remanded_to` | При отмене с направлением — куда направлено (1-я / апелляция). |
| `act_published`, `act_date`, `act_text` | Публикация и текст кассационного определения. |
| `suspended_until`, `hearing_date`, `hearing_time` | «Без движения» / дата заседания. |
| `events`, `link`, `last_checked_at` | Хронология, ссылка, отметка обновления. |
| `discovered_via_cassation` | Дублирует одноимённый флаг дела. |

### Повторные круги (`round` / `history`)

Если кассация отменила решение и направила дело на новое рассмотрение
(`outcome == "cassation_remanded"`), `_snapshot_round_to_history`
([строка 2132](../../scripts/court_monitor/lifecycle.py#L2132)) складывает текущие блоки
`first_instance`/`appeal`/`cassation` в `history[]` как снимок прошлого круга,
обнуляет их и увеличивает `round`. Дело начинает следить за новой карточкой
в нижестоящей инстанции «с чистого листа». Каждый элемент `history` хранит
`round`, `archived_at`, `reason` и три блока инстанций того круга.

## Архивы

### Горячий архив — `cases_archive.json`

Та же структура (`version`/`updated_at`/`cases`), что и `cases.json`. Содержит
дела, заархивированные **за последние 12 месяцев** (`COLD_ARCHIVE_DAYS = 365`).
Фронт грузит его и показывает во вкладке «Архив». У каждого дела добавляется
поле `archived_at` (`YYYY-MM-DD`) — якорь ротации.

### Холодные архивы — `cases_archive_YYYY.json`

Дела старше года выносятся ротацией (`rotate_cold_archive`,
[строка 968](../../scripts/court_monitor/linking.py#L968)) в годовые файлы по году
архивации. **Фронт их не загружает** — иначе вес скачиваемого браузером JSON рос
бы бесконечно. Скрипт читает их только в индекс дедупликации (`existing_ids`),
чтобы старое дело не всплыло как «новое». Холодные дела «заморожены»:
автоматическая реактивация их не сканирует, возврат — вручную через
`add_cases_manually.py`.

### Трек «Иски банка» — `cases_bank*.json` (split-хранение)

Иски самого банка (маркер `track: "plaintiff_light"`, целевой масштаб до
~3500 дел на территорию) живут в отдельных файлах, чтобы основной
`cases.json` не рос. С 26.07.2026 — **split-хранение**
(`load_bank_json`/`save_bank_json` в `storage.py`):

| Файл | Содержимое |
|------|-----------|
| `cases_bank.json` | активные записи **без** `first_instance.events` (та же схема + `track`) |
| `cases_bank_events.json` | `{"events": {"<домен>\|<номер>": [...]}}` — events отдельно (64% веса записи, фронту нужны только в drawer; ключ композитный — номера не уникальны между судами) |
| `cases_bank_archive.json` (+ `_events`) | горячий архив трека (≤365 дн), симметрично |
| `cases_bank_archive_YYYY.json` | холодные годовые — **полные записи с inline events** (write-only: фронт не грузит, прогон и импортёры читают только в дедуп-индекс) |

Пайплайн всегда работает со склеенными записями — split происходит только на
границе load/save, содержимое `events` не меняется ни на байт (инвариант
дедупа `(date, text)`). Ротация — общий `rotate_cold_archive` с
`path_builder=config.bank_cold_archive_path`. ⚠️ Перед `save_bank_json` базу
обязательно грузить `load_bank_json`: events-файл перезаписывается целиком.
Старый монолитный формат (events inline) читается прозрачно и мигрирует
первым же сохранением. Фронт грузит файлы трека лениво (тремя ступенями —
см. [08. Фронтенд](08-фронтенд.md)); архив и события подтягиваются по
требованию.

### Legacy CSV

[`data/sberbank_cases.csv`](../../data/sberbank_cases.csv) (+ архивный CSV) —
старый формат, **UTF-8 с BOM**, 20 колонок (`CSV_COLUMNS`,
[строка 434](../../scripts/court_monitor/config.py#L434)). Источником истины больше не
является, но всё ещё пишется и коммитится для обратной совместимости; фронт
использует его как фолбэк, если JSON недоступен.

## Чего нельзя делать

- **Не переименовывать поля** в `cases.json` без миграции — на них завязаны
  фронт (`jsonToCase` в `app.js`) и архивы.
- **Не писать BOM** в JSON. CSV — наоборот, с BOM (legacy-формат).
- **Не грузить холодные архивы во фронт** — это сводит на нет всю ротацию.
