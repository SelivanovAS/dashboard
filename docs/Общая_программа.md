# Общая программа и региональные установки

## Назначение

Источник разработки — `SelivanovAS/dashboard`, ветка `codex/program`.
Четыре рабочие ветки `main` остаются региональными установками:
`dashboard` (hmao), `dashboard-ural` (sverdlovsk_yanao),
`dashboard-bashkortostan` (bashkortostan), `dashboard-tyumen` (tyumen).
Обычные коммиты картотеки не меняют версию программы в `.program-release.json`.

Переход не меняет схему картотеки, адреса сайтов, подписки и порядок доставки.
Физические копии программы сохраняются ради совместимости с VPS, Pages и
Actions. Разработка ведётся в одном источнике, а установка — по команде.

## Профили и состав пакета

`deployment/manifest.json` перечисляет общие файлы по точным путям.
`deployment/regions/<region>/profile.json` задаёт территорию, репозиторий,
адрес сайта, путь VPS и отображение дополнительных файлов профиля в рабочее
дерево. Файлы настроек сайта, PWA и Worker сохраняют прежние форматы и значения.
README каждой территории также входит в её профиль: он сохраняет местные
инструкции и указывает на общий источник разработки. README исходной ветки
остаётся отдельным документом для разработки.
`deployment/baselines/<region>.json` фиксирует исходные хеши и режимы файлов
перед первым управляемым выпуском. Никаких значений секретов здесь нет.

`REGION` создаётся явно для каждой территории. У ХМАО остаётся прежнее
браузерное пространство без префикса; у Урала код Python `sverdlovsk_yanao`
отличается от браузерного пространства `ural`. Адреса Worker/KV и секреты
каждой территории не смешиваются. Внешние Actions Variables и env VPS имеют
прежний смысл; несовпадение эффективной территории требует разбора до установки.

В пакете нет рабочих `data/**`, журналов, runtime-каталогов, локальных env,
посторонних файлов и территориальных отчётов. Новые файлы исходника не становятся
управляемыми автоматически: их нужно добавить в точный manifest.
Удаление разрешено только для неизменённого файла прежнего управляемого выпуска.

## Подготовка и публикация

Использовать актуальные `scripts/program_release.py` и соседний
`program_install_vps.py` из ветки общей программы. Копия установщика в старом
региональном пакете может не содержать последующих исправлений процедуры.
Python 3.12 достаточен для инструментов выпуска; `scripts/requirements.txt`
и pytest нужны для полного набора тестов. Сначала сохранить исходник коммитом,
затем работать с его полным SHA. Грязное рабочее дерево не должно влиять на
содержимое пакета. Исправление установщика не меняет байты уже проверенного пакета.

Операции `scripts/program_release.py`:

- `build --source-sha <40-символьный SHA> --out <каталог> --regions <коды>`:
  воспроизводимая сборка без публикации.
- `plan --package <региональный пакет> --repo <региональный checkout> --region <код>`:
  проверка исходной описи/предыдущего паспорта и полный diff.
- `promote` с теми же параметрами готовит новый коммит только управляемых файлов;
  `--push --remote <SSH URL> --vps-host <SSH host> --ssh-key <путь>` публикует
  и устанавливает его. Исполняемые изменения требуют параметров общего окна,
  приведённых ниже. Без push это подготовка, а не установка.
- `--vps-host <SSH host> --ssh-key <путь>` дополнительно устанавливает опубликованную
  версию на VPS. Сначала выполняется проверка VPS только чтением, ещё до push:
  парсеры сами подтягивают `main`, поэтому отказ установщика после публикации
  был бы слишком поздним. При отказе предварительной проверки новый коммит
  не публикуется. Публикация рабочих территорий без обоих параметров запрещена:
  она позволила бы штатному `git pull` на VPS обойти проверку установщика.
- `verify --repo <checkout>` проверяет файлы установленной версии. Сетевые
  проверки включаются явно: `--remote <SSH URL>` проверяет опубликованную
  версию GitHub, `--site-url <URL>` — реальные файлы Pages, а
  `--vps-host <SSH host> --ssh-key <путь>` — установленную версию VPS.
  Эти проверки только читают состояние и не устанавливают программу,
  не изменяют таймеры и не запускают доставку.
- `rollback` применяет прежний проверенный пакет поверх актуальных данных новым
  коммитом. История Git, карточки, очереди и отметки доставки назад не откатываются.
  Первоначальный пакет возврата сохраняет ручной режим диагностических workflows;
  он не возвращает опасные автоматические пробы по push.

Пример полной проверки установленной территории без изменений:

```sh
python scripts/program_release.py verify --repo <checkout> --remote <SSH_URL> --site-url <URL> --vps-host <HOST> --ssh-key <KEY>
```

Без сетевых параметров результат относится только к локальному checkout.
Подтверждение GitHub, Pages и VPS не заменяет отдельную проверку Worker
и следующего штатного цикла парсинга и доставки.

Точные актуальные параметры выводятся через `--help` соответствующей операции.
Перед первым promote сохранить исходный пакет возврата через `build` с
`--baseline-repo <checkout>` и одной явно выбранной территорией.

Обычная публикация использует существующий SSH-доступ к GitHub через порт 443.
Стандартный `GITHUB_TOKEN` не подходит для централизованного push во все четыре
репозитория и не запускает Pages своим push. Боевые workflows материализуются
из шаблонов; source-ветка содержит только безопасные проверки.
Сетевые диагностические задания и вспомогательный сбор запускаются вручную.
Штатный replay сохраняет прежние условия по файлу контекста и маркеру доставки.

Новые data-коммиты во время выпуска сохраняются: пакет накладывается на свежий
HEAD. Изменение управляемого кода, профиля или паспорта останавливает операцию.
Повторный выпуск того же пакета не создаёт новый коммит. Для незавершённого
общего окна использовать `recover` с прежним каталогом операции; для новой
операции нужен новый каталог. Повтор уже завершённой операции только читает
сохранённый результат и проверяет его.

## VPS, Cloudflare и границы подтверждения

`program_install_vps.py` повторяет предварительную проверку и устанавливает
опубликованный коммит под штатными блокировками. Для ограниченного перехода
региональной копии без изменения исполняемой программы используется блокировка
только её клона. Установщик проверяет точный перечень изменений, неизменность
исполняемых файлов и настроек, фактические пути общих диспетчеров в systemd,
отсутствие неизвестных переопределений и незавершённых транзакций. В этом режиме
таймеры вообще не останавливаются и не запускаются. Занятость, неизвестное
изменение либо старая незавершённая установка останавливают выпуск.

### Общее окно для изменения исполняемой программы

Узкий прежний установщик не разрешает изменения Python-кода, оболочек запуска,
конфигурации и общих диспетчеров. Для них публичные `promote`, `rollback` и
`recover` используют независимый координатор, закреплённый точным коммитом.
Проверка только чтением перед push недостаточна: штатный парсер сам подтягивает
`main`. Поэтому координатор удерживает VPS с момента подготовки до завершения
проверенной установки или безопасной отмены.

Однократный `--bootstrap-guard` добавляет постоянное
`ConditionPathExists=!<state_dir>/blocked` к пяти рабочим службам. Он выполняет
`daemon-reload`, но не останавливает и не перезапускает таймеры. Расписания,
включение служб и их параметры сохраняются. Далее окно меняет только marker,
дожидается завершения уже работающих служб и их завершающих команд, проверяет
ожидающие задания и удерживает блокировки всех четырёх клонов. Установщик не
создаёт рабочие start jobs. Естественное задание таймера после проверки версии
само по себе не является ошибкой.

Этот порядок сохраняет совместимость с установленными старыми `run_lock.py`:
сначала запрещаются новые старты и завершаются старые helper-процессы, затем
координатор занимает их блокировки. Смерть процесса, обрыв SSH и перезагрузка
не снимают marker автоматически. Нельзя удалять marker, блокировки или журнал
вручную и нельзя использовать перезапуск таймеров для восстановления.

На systemd 255.4 перезапуск таймера мог вызвать внеплановый запуск службы
([systemd #31231](https://github.com/systemd/systemd/issues/31231)). Новый порядок
не использует этот механизм. ОС VPS и планировщик выпуском не обновляются.
Mac остаётся отключённым ручным резервом.

#### Подготовка конфигурации окна

Сохранить свежую опись четырёх VPS-клонов и защищённых файлов. Конфигурация
`--maintenance-config` содержит только пути, адреса репозиториев и паспорта:

- `schema_version: 1`, абсолютные `state_dir` и `config_dir`;
- `profiles`: четыре кода территории с `path`, `repository`, `remote`, `baseline`;
- `manifests`: карта `release_id` → полный паспорт каждого разрешённого пакета,
  включая текущий и подготовленный для возврата.

При существующем `.program-release.json` baseline должен точно ему соответствовать;
без паспорта нужна проверенная исходная опись. Не подменять неизвестное отличие
обновлённым baseline ради прохождения проверки. Секреты остаются в прежних env;
их значения не включаются в конфигурацию, пакеты, аргументы и отчёты.

Координатор собирается из Git-объектов полного `--coordinator-sha`, размещается
вне региональных клонов и не заменяется во время операции. Новый приватный
`--operation-dir` сохраняет его, копии пакетов, конфигурацию и журналы. Хранить
этот каталог до завершения и приёмки; при восстановлении использовать тот же
каталог, а не создавать новое окно поверх незавершённого.

Пример установки подготовленного регионального пакета:

```sh
python scripts/program_release.py promote \
  --repo <локальный_checkout_территории> --region <код> --package <пакет> \
  --push --remote <SSH_URL_территории> --vps-host <HOST> --ssh-key <KEY> \
  --maintenance-config <конфигурация_окна.json> \
  --coordinator-sha <точный_проверенный_SHA> --operation-dir <новый_каталог>
```

Только при первой подготовке добавить `--bootstrap-guard`. Не использовать
непроверенный коммит координатора. Исходный локальный checkout не изменяется;
рабочий кандидат и итог находятся внутри каталога операции. Последующий `verify`
выполнять в checkout фактически опубликованного коммита (например, `candidate`
из завершённой операции).

Каждый точный кандидат перед push передаётся отдельным Git bundle и сохраняется
на VPS. Лимит bundle — 512 KiB; превышение останавливает выпуск до push. Только
после регистрации и синхронизации журнала на диск выдаётся разрешение на
публикацию. Новые data-коммиты допускают новый кандидат поверх свежего HEAD;
все предыдущие targets и intents остаются в журнале. Неизвестное изменение
кода, настроек или паспорта останавливает операцию.

Перед записью клона сохраняется полная опись защищённых файлов и точный журнал
замен. Частичный checkout восстанавливается по этому журналу, без `reset --hard`,
`clean` и отката истории. Закрытые права обычных файлов данных (например 0600)
сохраняются при переносе новых данных и откате; проверка содержимого, специальных
битов и исполняемости остаётся строгой. Программа проверяется по паспорту.

#### Продолжение и возврат

```sh
# Продолжить то же окно после обрыва:
python scripts/program_release.py recover --operation-dir <тот_же_каталог>

# Отменить окно только если ещё не было намерений публикации:
python scripts/program_release.py recover --operation-dir <тот_же_каталог> --cancel-before-publish

# Перейти к заранее разрешённому пакету возврата в том же журнале:
python scripts/program_release.py recover --operation-dir <тот_же_каталог> --package <пакет_возврата>
```

Для обычного отката завершённого выпуска вызвать `rollback` с теми же полными
параметрами, новым каталогом операции и прежним проверенным пакетом. Возврат
создаёт новый коммит поверх свежих данных. При аварийном возврате все ранее
выданные разрешения push должны быть закрыты доказательствами; поздняя публикация
старого кандидата не должна заменить уже восстановленную программу.

`recovery_required` означает, что безопасный выход ещё не подтверждён. Сохранять
защиту и разбирать причину через журнал; не считать общий зелёный CI разрешением
обойти проверку. `cancelled` без attempts означает подтверждённую отмену до push.
`installed` и фаза complete означают установку и безопасный выход, но ещё не
доказывают Pages, работу внешней доставки или следующий обычный цикл.

#### Что проверяет репетиция

Изолированные workflows используют синтетические репозитории и службы без
боевых секретов: Python 3.12, настоящий systemd 255.4, SSH/Git, удержание четырёх
блокировок, SIGKILL во время checkout, реальную перезагрузку гостевой ОС,
восстановление того же окна, откат поверх новых данных и публичные команды.
Перезагрузка после SIGKILL не имитирует внезапное отключение питания. Точный SHA,
CI runs и артефакты принятой репетиции фиксируются в отчёте выпуска; отдельные
зелёные компонентные тесты не заменяют связанную проверку.

Общие диспетчеры запускают скрипт выбранного клона. Их изменение имеет общий
серверный эффект и проходит через то же окно. Сохранённые региональные пакеты
первого перехода и готовый пилот не пересобираются из-за доработки установщика.

Worker выкладывается отдельно только при изменении его кода/конфига. Отсутствие
нужной авторизации не является доказательством установки. Релизный отчёт
разделяет GitHub, CI, Pages, VPS, Worker и следующий штатный цикл. Службы
Тюменского шлюза и другие установленые nginx/systemd-конфиги автоматически
не переустанавливаются из-за появления их исходников в общем проекте.

Для Pages проверять реальные опубликованные файлы по хешам, включая паспорт;
для VPS — паспорт, хеши, эффективный REGION и состояние таймеров. Простого
совпадения HEAD или HTTP 200 недостаточно. Принудительный парсинг/replay и
тестовая рассылка не входят в проверку установки.

## Приёмка первого перехода

Сначала изолированные репетиции всех четырёх пакетов, затем ХМАО. После
подтверждённого обычного цикла ХМАО — по очереди Урал, Башкортостан и Тюмень.
Проверить сохранность картотеки, очередей, персональных подписок, результат
обычной доставки и отсутствие повторов. Штатная недоступность суда сама по
себе не означает дефект выпуска; сравнивать причину и данные конкретного прогона.

Исходный CI использует фиксированные тестовые данные. Полный pytest выполняется
в собранных региональных деревьях; отдельно проверяется выбор региона в новых
процессах вне conftest, который исторически фиксирует hmao. Перед установкой
проверять совместимость с копией актуальных данных без запросов и отправок.

Откат отрепетировать с более новыми данными. До завершения штатного цикла
состояние — «установлено, штатная работа ожидает подтверждения», а не
«внедрение завершено». Следующие территории не переводить при связанном с
переходом дефекте пилота.
