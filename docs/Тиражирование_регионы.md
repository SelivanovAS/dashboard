# Тиражирование на территории: регионы и форки

Дата: 15.07.2026. Контекст: система тиражируется на отделения Уральского банка
(этап 1 — Свердловская область + ЯНАО; Челябинск/Башкирия/Тюмень/Курган —
отдельное планирование после проверки этапа 1). Полный план —
`~/.claude/plans/reactive-singing-thacker.md` (сессия 15.07.2026).

## Архитектура: «эталон + связанные копии»

- **Этот репозиторий — эталон** и одновременно боевой инстанс ХМАО.
- **Территория = форк** со своим GitHub Pages, Cloudflare Worker + KV,
  Telegram-чатом (бот общий), секретами и данными `data/`.
- **Форк НЕ правит общий код.** Всё регион-зависимое задаётся:
  - Actions Variables форка: `REGION=<код>` (модуль в
    `scripts/court_monitor/regions/`), `DASHBOARD_URL`;
  - тремя «файлами территории»: `region_front.js` (URL Worker'а + VAPID public
    key + **`STORAGE_NS`** — обязательный неймспейс localStorage территории,
    напр. `'ural'`: фронты живут на одном origin github.io, без него
    звёзды/заметки/owner-секрет перемешиваются с ХМАО в общем браузере;
    эталон NS не задаёт), `manifest.json` (имя PWA),
    `cloudflare-worker/wrangler.toml` (name воркера, `[vars]`, id KV,
    сдвинутый cron).
- Обновление форка: `git fetch upstream && git merge upstream/main`. На файлы
  территории и `data/**` в форке настраивается merge-driver `ours` (эталон
  ежедневно коммитит ХМАО-данные — иначе каждый merge конфликтовал бы).

### ⚠️ Merge-драйвер `ours` НЕ защищает от НОВЫХ файлов эталона

Драйвер вызывается только при конфликте **содержимого** файла, который есть с
обеих сторон. Файл, впервые добавленный в эталоне, приезжает в форк обычным
добавлением — конфликта нет, драйвер не работает. Грабли живые: 26.07.2026
эталон завёл трек «Иски банка», и в форк уехали бы

- `data/cases_bank.json` — картотека Сургута. На территории это будит и
  бэкенд (`os.path.exists(JSON_BANK_PATH)` → прогон Урала полез бы опрашивать
  карточки ХМАО), и фронт (HEAD-проба 200 → сегмент «🏦 Иски банка» с чужими
  делами). Выключатель `BANK_TRACK=0` в Variables закрывает только первое:
  фронт про флаг не знает и сегмент покажет, поэтому файл надо **удалять**,
  флаг — второй замок, а не замена. (Сам флаг работает с 26.07.2026: до этого
  код его читал, а workflow не передавал, и переменная в Settings молча ничего
  не делала.);
- `ops/bank_registry/**`, `ops/writ_probe/**` — ХМАО-данные;
- `.github/workflows/{collect_bank_claims,probe_writ_section}.yml` — у обоих,
  помимо `workflow_dispatch`, есть `push:` с фильтром по путям своих же
  файлов. То есть merge, который эти файлы приносит, их же и **запускает** —
  на форке, с `contents: write`, по судам ХМАО.

**Порядок синхронизации:** после `merge` смотреть `git status` на предмет
новых `data/**`, `ops/**` и workflow'ов эталона и удалять чужие через
`git rm`. В форке эти пути перечислены в `.gitattributes` — там же указано,
что следующий merge даст по ним конфликт `modify/delete`, и разрешать его
надо `git rm`, а не «взять версию эталона». Территория, которая заводит трек
у себя, делает свой `ops/bank_registry/registry.csv` — ХМАО-шный тянет дела
Сургута.

## Регион как конфиг

- Типы — `scripts/court_monitor/regions/base.py`: `CourtConfig` (+ override-
  поля `delo_table/name_field/new_param` для нестандартных кассаций, напр.
  6-й КСОЮ Башкирии) и `RegionConfig` (код, имя, `appeal_courts` — **кортеж,
  апелляций может быть несколько**, реестр FI, кассация, маркеры матчера,
  `dashboard_url`, `public_info()` для фронта, `health_cassation_keys()`).
- Регионы — по модулю на территорию: `regions/hmao.py` (эталонный),
  далее `regions/sverdlovsk_yanao.py` и т.д. Все регионы живут в эталоне.
- Выбор — env `REGION` → `config.REGION` → `regions.get_region()` (ленивый
  importlib; неизвестный код падает громко). `courts.py` — фасад активного
  региона: `APPEAL_COURTS`/`APPEAL_COURT`/`FIRST_INSTANCE_COURTS`/
  `CASSATION_COURT` + `match_region_first_instance(name, region)`
  (`match_hmao_first_instance` — legacy-обёртка по активному региону).

## Мульти-апелляция (Свердловск+ЯНАО = облсуд + Суд ЯНАО)

- Блок `appeal` в cases.json хранит `court` / `court_domain` / `delo_id`;
  бэкфилл старых записей — `migrate_appeal_court_fields` (lifecycle, зовётся
  рядом с `migrate_stages`).
- Поиск апелляции в `main_json` — цикл по `APPEAL_COURTS`; карточки строятся
  по домену дела (`appeal_court_by_domain`).
- Связка `link_cases` ключуется парой `(домен апел-суда, номер)` — номера
  `33-…/YYYY` между двумя судами не уникальны.
- Дайджест показывает имя апел-суда только при нескольких судах в регионе
  (`details["appeal_court"]`); фронт берёт подпись/ссылку из `appeal.court*`.

## Фронт и инфраструктура

- Бэкенд пишет блок `region` в cases.json (`RegionConfig.public_info`) —
  app.js строит из него подписи/ссылки кассации (и апелляций — из полей дела)
  с ХМАО-фолбэком для старых данных.
- Worker: `ALLOWED_ORIGIN` / `CASES_DATA_URL` / `GH_REPO` — из `[vars]`
  wrangler.toml (фолбэки в коде = боевые значения ХМАО; чтобы vars
  применились, нужен `wrangler deploy`).
- Имена источников в админке «Здоровье парсеров» — из `parse_health.json`
  (поле `label` пишет `health.py`); карта `COURT_NAMES` в admin_page.js —
  временный фолбэк, удалить после пары прогонов.

### Капча на АПЕЛЛЯЦИИ (Свердловский облсуд, 25.08.2026)

25.08.2026 проверочный код появился и на апелляции. Диагноз по данным
прогона Урала: `last_run.fail_kinds = {"captcha_search": 1}`, счётчик
`appeal:oblsud--svd` упал `24 → 0` при живых 23 у Суда ЯНАО, а карточки
облсуда в тот же прогон читались штатно (69 из 118 дел стадии `appeal`).
Модель прежняя: код закрывает ПОИСК, карточки живут.

Цена потери канала выше, чем у одного суда 1-й инстанции: поиск апелляции —
это вход дел «сверху» (118 из 316 активных дел территории — облсуд, а 1-я
инстанция там вся за кодом) плюс связка дел, ушедших наверх (они висят в
`awaiting_appeal`, а эта стадия не архивируется никогда).

**Гейт МЯГКИЙ** (решение юриста): `search_gated=True` у апелляции значит не
то же, что у 1-й инстанции. Суд ОСТАЁТСЯ в обходе поиска — прогон делает
свой один запрос, — но капча на помеченном суде считается штатным режимом:
нет 🩺-алерта «требует ввод проверочного кода», нет Telegram-warning «вернул
0 дел, но в CSV N активных», в журнал здоровья пишется «не наблюдали»
(`None`), а не ноль (ноль детектор молчаливой поломки читает как аварию).
Снимут код — автопоиск вернётся сам, без коммита и деплоя. ⚠️ На суде БЕЗ
флага капча по-прежнему кричит: это новая авария, а не режим.

Дослинк `relink_awaiting_appeal` ходит ТОЙ ЖЕ поисковой формой, поэтому
получает `skip_domains` — домены, чей поиск закрыт В ЭТОМ прогоне (гейт по
факту, а не по флагу: снятый код чинит и дослинк тем же прогоном).

Дела заводит дамп выдачи — ветка апелляции того же импортёра (ниже).

**28.08.2026 мягкий режим у облсуда отменён юристом** — второй флаг
`search_disabled=True` (`CourtConfig`): поиск облсуда прогон не делает
ВОВСЕ — ни HTTP, ни записи в журнал здоровья. Причина: мягкий гейт писал
`None`, а `update_parse_health` считает `None` HTTP-фейлом и растил
`fail_streak` — «страница поиска не загружается 16 прогонов подряд» шумело
каждым слотом (🩺 + WARNING). Ветка стоит ПЕРВОЙ в цикле фазы 3 (до дочитки
и до `fetch_page`) и сама кладёт домен в `appeal_search_gated_now` — иначе
дослинк, чей skip наполнял капча-детект, снова жёг бы HTTP по капчёвой
форме. `search_gated` при этом ОСТАВЛЕН: он гейтит семантику дампов,
бэкфиллы и админку. Карточки облсуда мониторятся как раньше; канал ввода
новых дел — только дамп. Возврат автопоиска (если суд снимет код) — снять
`search_disabled` в конфиге региона и задеплоить. Застывшая запись
`appeal:oblsud--svd.sudrf.ru` из `data/parse_health.json` форка удалена
разово (label/obs больше не пишутся — сама она не пересоздастся, а
`fail_streak`=16 красил бы админку красным вечно). Стражи —
`TestSearchDisabled` в test_appeal_gated_search.py.

**04.09.2026 — код закрыл поиск и Суда ХМАО-Югры** (`appeal:oblsud` 21→0
семь слотов подряд, `last_run.fail_kinds.captcha_search`; карточки читались
31/31). Режим — как у СВД, решение юриста: оба флага у `APPEAL_COURT` в
`regions/hmao.py`. Рецепт включения дампа на любой территории — три шага:
(1) флаги в `regions/<регион>.py`; (2) точечная правка блока `region` в
`data/cases.json` (`appeal_courts[].search_gated/search_disabled`, `updated_at`
не трогать — иначе админка увидит суд лишь после следующего прогона);
(3) удалить застывший ключ источника из `data/parse_health.json` (`indent=1`).
Ни Worker, ни админка, ни импортёр правок не требуют — всё читает реестр.
У ХМАО `OPERATOR_SECRET` не задан: дампы вставляет сам юрист под owner.
Очередь дочитки на VPS для территории работает только при
`~/.config/court-monitor/worker.<регион>` — для ХМАО его надо завести
(ветка апелляции карточку требует обязательно, `[FETCH FAIL]` = потеря строки).

**Алерт «суд стал капчёвым» (04.09.2026).** Капча на поиске ЛЮБОГО
непомеченного суда (1-я инст., апелляция, кассация) теперь ведётся
капча-состоянием `update_parse_health` (health.py; поля записи источника
`captcha_since`/`captcha_alerted_on`, проводка — `health_captcha`
{ключ журнала: домен} в runs.py): 🔐-алерт с рецептом при первом обнаружении,
напоминание раз в день, пока суд не помечен в конфиге, ✅ «код снят» при первой
странице без кода; дубль «поиск вернул 0» для такого ключа глушится. Прежний
алерт «требует ввод проверочного кода — проверить вручную» повторялся каждый
прогон и — главное — с флипа на Mac/VPS не доходил до Telegram вовсе
(Python там без токена); теперь строки детектора лежат в `last_run.alerts`,
а `parse_and_push.sh` ретранслирует их shell-каналом
(`cloud_run_ok.py --health-alerts`, дедуп по строке за день).

### Кассация в ПРЕЗИДИУМЕ облсуда — дела мировых судей (04.09.2026)

С мая 2026 (ГПК) кассационные жалобы на акты, вынесенные в 1-й инстанции
МИРОВЫМИ судьями, рассматривают президиумы областных судов, а не КСОЮ.
На сайте облсуда это раздел `delo_id=2800001&new=2800001` — тот же домен,
что у апелляции; поиск за проверочным кодом (проба ХМАО 04.09.2026) →
новые дела только из дампа. Карточки открыты и читаются парсером 7kas
(`parse_cassation_card`): УИД мирового судьи `86MS…`, номер 1-й инст.
`2-1543-2803/2019`, «Судья (мировой судья) первой инстанции: ФИО (участок)»,
кассатор, участники (роли ВЗЫСКАТЕЛЬ/ДОЛЖНИК — приказное производство).

**Модель.** `RegionConfig.presidium_courts` — ещё один реестр
(`court_type="cassation"`, `search_gated`+`search_disabled`); КСОЮ
(`cassation_court`) остаётся один, ⚠️ в `appeal_courts` президиум не класть
(`_appeal_health_key`). Суд блока `cassation` решает
`cassation_court_by_domain(court_domain)`: по нему фаза 4d перечитывает
карточку, дайджест и фронт строят ссылку. Ключ кассационного производства —
ПАРА (домен, номер): «4Г-N/YYYY» двух президиумов Урала совпадают.
Главный номер дела — номер президиума «4Г-…» (решение юриста), номер
мирового судьи — в стабе `first_instance` с флагом `magistrate: true`;
такие номера в индексы дедупа 1-й инстанции не попадают (иначе wildcard
заблокировал бы районное дело с тем же номером). Remanded у президиума не
уводит в `awaiting_relink` — нижестоящих не мониторим, архив по окнам.

**Дамп.** Та же вкладка «Импорт», третья закреплённая строка «… —
президиум (кассация)» с кнопкой в раздел 2800001. Раздел выбирает САМ ДАМП:
`resolve_court(domain, delo_id=)` по `delo_id` из ссылок карточек —
оператор шлёт голый домен, Worker/workflow/очередь VPS без правок; в
админке автоопределение тоже по `delo_id`. Ветка `_main_presidium`:
строки с датой поступления до реформы (`PRESIDIUM_DUMP_SINCE`=01.05.2026)
— `[SKIPPED OLD]` без карточки (выдача по «Сбербанк» тянет дела
президиума-2019: 22 из 25 в первом дампе ХМАО), карточка обязательна
(`[FETCH FAIL]` = потеря строки, очередь резерва переделает), без ПАО
Сбербанк в участниках — `[NO SBER]`; приём — боевой `link_cassation_cases`
(`[ADDED PRESIDIUM]` / `[LINKED]` по УИД/номеру), CSV не пишется. Новые
дела получают `import.source="dump_presidium"` и объявляются один раз в
«📥 Новые касс. дела» (`announce_imported_presidium_cases`). Отчёт несёт
`section` (строка) и `skipped_old` — правило трёх звеньев (jq → Worker →
админка). Свежесть `import:last:<домен>` общая с апелляцией того же домена
(как у площадок: оператор берёт обе выдачи за один заход). Стражи —
`scripts/tests/test_presidium_cassation.py`, `test_import_presidium_dump.py`;
фикстуры — реальные страницы Суда ХМАО-Югры (обезличены).

### Полнота реестра: две разные проверки (14.08.2026)

**1. Вторые площадки существующих доменов** — режим `--scan-servers`
(галка в workflow). Судебное присутствие живёт на домене суда отдельным
сервером `srv_num=2+` (Покачи на `vartovray--hmao`), и без записи в конфиге
такой суд невидим целиком. ⚠️ Первый прогон по Уралу (14.08.2026) не нашёл
ни одного присутствия: все четыре вторые площадки — картотеки **уголовного
судопроизводства** (Верх-Исетский, Кировский, Орджоникидзевский — «Уголовная
коллегия»; Железнодорожный — «Уголовные дела и дела об административных
правонарушениях»). Решение юриста: уголовные картотеки в мониторинг не
берём. **Правило: площадку в конфиг — только с гражданской подписью**;
классификация идёт по ПОДПИСИ, а не по номеру — у Железнодорожного
гражданская картотека как раз на srv 2, уголовная на srv 1. Проба печатает
подписи всех площадок (включая уже заведённые) и флажит «⚠ В КОНФИГЕ НЕ
ГРАЖДАНСКАЯ ПЛОЩАДКА»: так ловится обратный дефект — уголовная картотека,
попавшая в реестр вслепую.

**2. Целиком пропущенный суд** — `--scan-servers` его НЕ увидит (ходит
только по доменам конфига). Проверяется вручную, автоматики нет осознанно
(решение юриста 14.08.2026): перечень судов субъекта берётся с портала ГАС
«Правосудие»

    https://sudrf.ru/index.php?id=300&act=go_search&searchtype=fs&court_subj=<код>&court_type=RS

(коды субъектов: 66 — Свердловская обл., 89 — ЯНАО, 86 — ХМАО) и сверяется
с `get_region().first_instance_courts` **по домену**, не по названию
(названия в перечне длинные, с «…области»). Так 14.08.2026 нашёлся
незаведённый **Приуральский районный суд ЯНАО** (`priuralsky--ynao.sudrf.ru`,
Аксарка) — 13-й суд округа при 12 в конфиге; по Свердловской области
совпадение полное (52 = 52). Найденный суд сначала прогоняется обычной
CSV-пробой (строка в `ops/region_probe/courts_probe.csv` ФОРКА — push сам
запустит), она проверит delo_id и капчу, и только потом заводится
`CourtConfig`.

⚠️ Отчёты `ops/region_probe/**` — территориальные: пробу с эталона не
запускаем, иначе при следующем merge форк получит конфликт add/add по
`servers_report.txt`. Путь самого workflow убран из `push.paths` — merge
правки этого файла в форк раньше запускал пробу на территории без спроса.

## Импорт дел капчёвых судов

**Роли админки.** У Worker'а два секрета: `OWNER_SECRET` (юрист-владелец,
всё как раньше) и `OPERATOR_SECRET` (ОДИН общий на всех сопровождающих;
имя оператора — поле формы, доверительное). Оператор по ссылке
`…/admin?secret=<OPERATOR_SECRET>` видит статус, здоровье парсеров, живой
лог и секцию «Импорт дел»; подписчики, LLM-тесты и запуск прогонов закрыты
и в UI, и НА СЕРВЕРЕ (403). Не задан `OPERATOR_SECRET` (ХМАО) — роль
неактивна. Утечка секрета = ротация `wrangler secret put OPERATOR_SECRET`
и перераздача ссылки.

**Инструкция оператора (сопровождающего суда):**
1. Открыть сайт своего суда (кнопка «Открыть сайт суда» в админке) →
   «Судебное делопроизводство» → поиск по делам, ввести «Сбербанк»,
   решить проверочный код. ⚠️ Первой строкой списка стоит
   **«Свердловский областной суд — апелляция»** (у ХМАО с 04.09.2026 —
   «Суд ХМАО-Югры — апелляция»): с 25.08.2026 код закрыл и
   её, а раздел там СВОЙ (кнопка ведёт прямо в него). Этот суд закреплён —
   он один на территорию, виден всем операторам и в набор «мои суды» не
   убирается.
2. На странице результатов: выделить всё (Ctrl+A) → копировать (Ctrl+C).
   Либо сохранить страницу как «Веб-страница, только HTML» (.html).
   ⚠ Вставка «как текст» не годится — теряются ссылки на карточки дел
   (такие строки импортёр пропустит с пометкой `[NO LINK]`).
3. В админке, секция «Импорт дел»: выбрать суд, вписать своё имя (одно поле
   в шапке вкладки, помнится в браузере), вставить скопированное в поле
   (или приложить сохранённый файл) → «Отправить на импорт».
4. Ждать на странице: «в очереди → выполняется → вердикт» (обычно 1–3 мин;
   таймер тикает с первой секунды). Вердикт отвечает на главный вопрос
   одной фразой: «Готово: заведено N дел» / «Ничего не заведено — карточки
   не открылись, нужен повтор дампа». Под ним — «Проблемы», «Заведено»,
   «Пропущено» и свёртка построчного отчёта; история — в свёртке «История
   импортов». Нет ответа ~5 мин — повторить отправку (дамп живёт в KV 24 ч),
   не помогло — сообщить владельцу.

**Один раз при первом заходе — отметить «мои суды»** (свёртка «Свежесть по
судам» → «Отметить мои суды»). Секрет оператора ОДИН на всех сопровождающих,
и без набора каждый видит очередь на все капчёвые суды территории (на Урале
их 56), а форма подставляет самый просроченный суд из общих — почти наверняка
чужой. С набором наверху идут свои суды рабочей очередью, остальные — в
свёртке «Прочие суды», а бейджи и плитка пульта «Импорты» считают по своим.
Набор живёт в localStorage браузера: на сервер не уезжает, у каждого свой,
пустой набор = прежнее поведение «все суды».

⚠️ **Красный суд, импортированный сегодня** — не ошибка светофора: регламент
не засчитывает импорт, у которого суд не отдал карточки (тот же гейт, что на
сервере). В строке такого суда стоит пометка «⚠ попытка <когда>: карточки не
читались» с причиной в подсказке, а в пульте — плитка «Карточки судов».
Лечится повторным дампом, когда суд отвечает.

Светофор показывает **12 самых просроченных судов**, остальные — в свёртке
«Остальные N судов» (на территории их 54, и без потолка список занимал
четыре экрана телефона). Клик по строке выбирает суд в форме и внутри
свёртки тоже.

⚠️ **Карточка «Здоровье парсеров» на вкладке «Система» про капчёвые суды не
знает ничего** — `parse_health.json` наполняется только по `courts_for_search`,
а он исключает `search_gated`. Её «все N ok» — про суды с открытым поиском;
охват подписан прямо в карточке.

**Механика под капотом.** `POST /admin/import-dump` кладёт дамп в KV
(`import:dump:<uuid>`, TTL 24 ч) + запись журнала (`import:log:<ts>|<uuid>`,
TTL 90 дн) и диспатчит `import_cases.yml` (роль проверяется на сервере:
`DISPATCH_WORKFLOWS.roles`). Workflow забирает дамп (`GET /import-dump`,
Bearer `PUSH_SECRET`, свой User-Agent), гонит офлайн-импортёр
[scripts/import_search_dump.py](../scripts/import_search_dump.py)
(utf-8→win-1251, нормализация pretty-print, детект капчи; дела
«банк-ответчик» → основная картотека cases.json — как в автопоиске; с
13.08.2026 (разгон Урала) строки «банк-истец» заводятся в трек «Иски
банка» (`cases_bank.json`): правила приёма общие с авто-подхватом
(`bank_intake`: `row_passes`/`card_rejects(skip_appeal=False)` — дела с
жалобой берутся и первым прогоном переезжают в основной cases.json /
`make_bank_entry(source="dump")`/`entry_is_spent` + негативный кэш
`.bank_intake_seen.json`, no_link в кэш НЕ пишется — ссылку обычно теряет
вставка «как текст», а не выдача), по ссылке из дампа качается КАРТОЧКА
дела — единственный онлайн-шаг импортёра (капча закрывает только поиск),
кэп-страховка `MAX_BANK_CARDS_PER_IMPORT`=100 на импорт (повтор того же
дампа безопасен — дедуп отсеет), маркеры `[ADDED BANK]`/`[EXCLUDED
RESULT]`/`[EXCLUDED WRIT]`/`[SPENT]`/`[SEEN]`/`[FETCH FAIL]`/`[BANK
CAPPED]`, дела в дайджесте НЕ анонсируются (`import.announced=true`); при
`BANK_TRACK=0` истцовые строки идут прежним `[SKIPPED ROLE]` (решение
юриста 16.07.2026, принималось до появления трека); «третье лицо» —
всегда `[SKIPPED ROLE]`; отсев дочек, дедуп через `collect_fi_dedup_index`
по ВСЕМ картотекам (активные + архивы + bank-файлы), `srv_num` из href
дампа; строка с
комбо-номером «2-X ~ М-Y» при уже отслеживаемом материале М-Y
переименовывает запись — `[PROMOTED]`, зеркало промоушена main_json,
дубль не создаётся), коммитит
cases.json («📥 Импорт: суд +N (оператор)») и постит итог в
`POST /import-result`. **С 18.08.2026 ветка «банк-ответчик» выровнена с
истцовой** (разбор юриста): карточные фильтры приёма — второй рубеж «иск
не принят к производству» по карточке (`[NOT ACCEPTED]` … «итог из
карточки») и «давно решённое — тихо сразу в архив» по строке или карточке
(`[ADDED OLD]`, счётчик `resolved_old`, «новым иском» не объявляется, при
поздней жалобе дело реактивируется из архива); негативный кэш
`.bank_intake_seen.json` теперь ОБЩИЙ — карточные отказники ответчик-ветки
при повторе дампа отвечают `[SEEN]` без HTTP; «суд не в реестре региона» —
честная причина `no_court` в `card_failed` (раньше пряталась за «за
кэпом»); дочитка `[REFILLED]` записи ТРЕКА (кросс-трековое совпадение
номера) сохраняет `cases_bank.json`, строка несёт хвост «(иски банка)».
Card-blind заведение при недоступной карточке сохранено — иск против
банка не теряется. Concurrency-группа `cases-data-write` общая с
основным прогоном — записи в data/ сериализованы. Карточки добавленных дел
дозаполняет ближайший прогон; он же ОБЪЯВЛЯЕТ их «новыми исками» в дайджесте
и общем пуше — ровно один раз (`announce_imported_cases` в runs.py, флаг
`import.announced`). Служебный блок дела —
`"import": {operator, at, source, announced}`.

**Ветка АПЕЛЛЯЦИИ (25.08.2026).** Отдельного скрипта и workflow нет: суд
выбирается доменом, а ветку импортёр берёт из реестра региона
(`resolve_court` ищет и среди `appeal_courts`, дальше решает `court_type`).
Общее — приём дампа, гейты (код в дампе, чужой хост, чужой раздел по
`delo_id`), отчёт, журнал и очередь резерва на Mac. Своё:

- строки разбирает `parse_search_page` (выдача апелляции), роли не делятся —
  наверх едут дела с любой ролью банка, как и в боевом поиске;
- **карточка ОБЯЗАТЕЛЬНА**: номер дела 1-й инстанции суд публикует только в
  ней, а без него запись не с чем связывать. Нечитаемая карточка = строка
  потеряна (`[FETCH FAIL]`, счётчик `fetch_fail`, сводка говорит «N дел
  апелляции не заведено»), повтор берёт очередь резерва. Card-blind заведение
  здесь было бы хуже потери: получился бы вечный двойник известного дела —
  `link_cases` в прогоне питается той же выдачей, что за кодом;
- связка — БОЕВОЙ `link_cases`: есть дело 1-й инстанции → апелляция вливается
  в него (`[LINKED]`, счётчик `linked`, стадия → `appeal`), нет → запись живёт
  сама (`[ADDED APPEAL]`, id остаётся апелляционным — как у 122 из 142
  «дел с апелляции» боевого Урала). Щит от сирот — `dedupe_orphan_by_base_number`;
- пишутся ДВА файла: `cases.json` **и CSV**. Строка CSV не наследие: обход
  карточек апелляции в прогоне (`update_active_cases`) идёт ПО СТРОКАМ CSV, и
  дело без строки не перечитал бы никто. Поэтому же коммит-шаг
  `import_cases.yml` переведён на общий `ops/stage_data_files.sh` — ручной
  перечень файлов к этому моменту уже был неполон;
- **анонс** (решение юриста): дело из дампа объявляется ровно один раз в
  апелляционной секции «📥 Новые дела» ближайшим прогоном
  (`announce_imported_appeal_cases`, `import.source = "dump_appeal"`). Дело,
  приклеенное к известной 1-й инстанции, не объявляется вовсе: наверх уехало
  известное дело, «новым» его называть нельзя (служебный блок `import`
  исчезает вместе с записью-сиротой при слиянии — специально).

**Защита «дамп ↔ выбранный суд» (17.07.2026).** Ошибка «выбран суд А,
вставлена выдача суда Б» давала бы немониторимое дело: суд записи — из
dropdown, а `case_id`/`case_uid` — из href дампа, ссылка на карточку выходит
битой. Настоящий суд виден в дампе по хостам абсолютных ссылок карточек
(rich-paste абсолютизирует href `https://<суд>/modules.php?…name=sud_delo…`)
и маркеру Chrome «saved from url=…» в файле «только HTML». Три уровня:
админка **сама подставляет** распознанный суд в dropdown (пока оператор не
выбирал вручную; конфликт — заметка «⚠ ссылки ведут в …» + кнопка «выбрать
этот суд», отправка блокируется), Worker отвечает 400 (`detectDumpSudrfHosts`),
импортёр падает с `EXIT_WRONG_COURT=5` (`detect_dump_hosts`) — текст ошибки
оператор видит в журнале импорта. Требуется ровно один хост, равный
выбранному; дамп без хостов (относительные href, файл Firefox) проверки не
триггерит. Дополнительно `delo_id` из href карточек ловит выдачу не того
раздела (апелляция=5, кассация=2800001) даже без хостов — суды 1-й инстанции
он не различает (у всех 1540005). С 25.08.2026 гейт работает и в обратную
сторону (выдача 1-й инстанции, отправленная как дамп апелляции), а текст
отказа называет НУЖНЫЙ раздел — он же разный у веток.
