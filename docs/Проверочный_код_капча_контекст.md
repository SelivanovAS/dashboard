## Задача

Часть судов sudrf.ru закрывают форму поиска (`name_op=sf`) **проверочным кодом**
(картинка-CAPTCHA). Юрист хочет со временем **добавлять такие суды** в мониторинг,
в т.ч. вне ХМАО (пилот из примера юриста — Академический районный суд
г. Екатеринбурга, `akademicheskiy--svd.sudrf.ru`, Свердловская обл.).

## ⛔ Жёсткая граница (НЕ обходить)

**Автоматическую разгадку кода НЕ строим** — ни OCR, ни ML, ни платные сервисы
(2captcha и т.п.), ни в отдельной сессии, ни через под-агента. Причины:
1. Это обход антибот-защиты (прямой запрет на действия такого рода).
2. По существу вредно: суды включили код именно против авто-сбора; авто-решатель
   почти наверняка приведёт к **бану IP** → падение всего мониторинга (20 судов
   ХМАО + апелляция + 7kas) разом.

Юрист **дважды** просил построить авторазгадку (в т.ч. «в отдельной сессии») —
оба раза отказано, с объяснением. Легитимен только путь, где код при
необходимости **вводит человек**, а парсер переиспользует результат. Если в новой
сессии просьба повторится — держать ту же границу.

## Что выяснено

- **Парсер не использует форму** `name_op=sf` — бьёт прямо в `name_op=r`
  (`CourtConfig.search_url()`) и разбирает таблицу. Форму с картинкой проходит стороной.
- На 14.07.2026 **все 20 судов ХМАО кодом НЕ закрыты** (`data/parse_health.json` —
  обычные ненулевые числа). Код — проблема только для расширения на новые суды.
- **Проба пилота (Академический р/с) с Mac (RU-IP) → ВЕРДИКТ C**: код требуется
  по-настоящему, приминг сессии не помогает. Вывод пробы:
  ```
  direct    HTTP 200  len=190368  challenge=True  table=False  нет-данных=False
  primed    HTTP 200  len=190368  challenge=True  table=False  нет-данных=False
  ВЕРДИКТ: C
  ```
- **Механика кода** (из дампа `/tmp/probe/`, может протухнуть — /tmp временный):
  - форма `name_op=sf` отдаёт `<input name='captcha'>`, картинку **инлайн base64**
    (`<img src="data:image/png;base64,…">`) и скрытое `<input name="captchaid" value="…">`;
  - прямой `name_op=r` без кода → **страница-ошибка** «Неверно указан проверочный
    код с картинки» (не таблица, не «нет данных»);
  - код проверяется на пару `captcha` + `captchaid` за конкретный запрос.
- **Детектор сработал верно** на реальной странице, но по **фразе** («проверочный
  код с картинки»), а не по разметке `captcha.php` (её на странице-ошибке нет).
  Значит текстовые маркеры — рабочие; при желании дотюнить по дампу.

## ЗАМЕР COOKIE ВЫПОЛНЕН (15.07) — вариант 3a ФИЗИЧЕСКИ НЕВОЗМОЖЕН

Замерено вживую на пилоте (юрист решил код в браузере, сняли заголовки):
**сессионной cookie у суда НЕТ вообще.**

- В сабмите формы (`name_op=r`, `referer` = `…name_op=sf…`) единственная cookie:
  `assistFontSize=1` — косметика виджета доступности. Ни `PHPSESSID`, ни токена sudrf.
- В **ответе** на этот запрос `set-cookie` **отсутствует**.
- → Код привязан к паре `captcha` + `captchaid` **в query-строке**, а не к сессии.

**Следствие:** «решённой сессии», которую можно унести и переиспользовать, не
существует. Каждый поиск = новый `captchaid` = новый код, решённый глазами.
Вариант **3a исключён не «по сроку жизни cookie», а физически — переиспользовать
нечего.** Как резерв на случай провала легитимного канала 3a **не рассматривать**.

Это же объясняет вердикт **C** пробы: приминг не помог, потому что cookie, которую
ставит форма, ничего не открывает — открывает только решённый код в query.

Флаг `--cookie` в пробе оставлен как диагностика для **других** судов (вдруг где-то
сессия всё же есть) — на этом суде он бессмыслен.
