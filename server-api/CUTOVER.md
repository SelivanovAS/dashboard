# Переход ХМАО на серверный API

Подготовка не включает переключение. Рабочие API, DNS, Cloudflare Worker,
KV и рассылки до отдельного поручения остаются действующими.

## Что меняется при первом переключении

Профили, подписки, календари, посещения, прогресс и очередь API переходят
из KV в SQLite на новом VPS. Прежние адреса, пользовательские ключи,
ссылки календарей и публичный VAPID сохраняются. Временный Worker-переходник
принимает основной и резервный адреса и передаёт запросы закрытому API.
Действующие секреты остаются в Cloudflare; отдельные внутренние ключи создаются
для переходника. GitHub PAT также остаётся в Cloudflare.

Исполнитель `/opt/court-monitor/dashboard`, очередь импортов VPS, публикация
GitHub/Pages и обычная доставка сохраняются. Серверный API работает с
`executor: legacy-vps`; запуск второго местного обработчика запрещён.
Индекс календаря проверяется по двум файлам прежней картотеки каждую минуту,
при свободной региональной блокировке и совпадении хешей до/после копирования.
Индекс, который не сверялся более часа, даёт календарю 503.

Отдельный закрытый пилот `/srv/projects/sbersud/pilot/hmao` служит для проверки
дампов, пачек, обычного разбора карточек, публикации и восстановления. Его данные
не публикуются в рабочий Git/Pages. Его результаты не подменяют рабочую картотеку.

## Подготовленные компоненты

Рабочая копия API: `/srv/projects/sbersud/api/hmao`, порт **127.0.0.1:18181**.
Каталог `prepared/` доступен только root и содержит:

- `nginx-location.conf` — закрытый путь в существующем HTTPS-сервере monitor:8443;
- `wrangler-bridge.toml` и `code/` — точный пакет переходника;
- `cloudflare-new-bindings.json` — только новые внутренние ключи. Не включать их в отчёты.

Генератор `prepare-transition.py` требует пустое отдельное состояние. Он не
устанавливает публичный маршрут и не выкладывает Worker. Конфигурация имеет
`executionEnabled: false`: запуск задач и внешняя отправка закрыты. Включены
только API на loopback и проверка индекса; таймеры dispatch и cleanup до
переключения выключены. `/admin/test-push` намеренно возвращает 503, в том числе
после первого переключения; обычная доставка остаётся в прежнем конвейере.

GitHub-запуск сначала фиксируется в SQLite, затем обрабатывается отдельной
службой. Разрешены только прежние workflows своего репозитория. При потере
ответа результат становится `uncertain` и автоматически не повторяется.
Перед ручным повтором требуется проверить историю GitHub. Эта очередь не
заменяет обычный VPS-поллер дампов и пачек.

## Окно переключения — только после отдельного поручения

1. Проверить свежесть резервной копии, свободное место и действующий токен
   чтения KV. Подготовленный токен истекает 19 ноября 2026 года, 18:59:59 UTC.
   Сверить текущие рабочие версии Worker, VPS и регионального паспорта.
2. Дождаться отсутствия работающих задач ХМАО на VPS и в GitHub. На время окна
   приостановить приём и всех писателей ХМАО согласованным координатором из
   `docs/Перенос_исполнителя_2026-11-12.md`. Блокировки не удалять. Не запускать
   старый VPS. Остальные территории не переводить на новый API.
3. Сохранить точную прежнюю версию Worker и его настройки для возврата до
   первой новой записи. Добавить только новые bridge bindings. Выложить
   переходник с `BRIDGE_MAINTENANCE=1`: все клиентские маршруты возвращают 503,
   прежний scheduled cleanup ничего не пишет. Проверить основной и резервный
   адреса. Только после этой проверки считать прежний KV замороженным.
4. Сделать два полных совпадающих чтения KV. Сохранить все ключи, metadata и
   абсолютные сроки; не отбирать только известные префиксы. Остановить новую
   API-копию и индекс, сохранить её репетиционное состояние отдельно и создать
   пустую SQLite из окончательной выгрузки. Сверить весь снимок, профили,
   календари и подписки. Прежний KV оставить нетронутым.
5. Сформировать актуальный индекс прежней картотеки. Сделать согласованную
   резервную копию новой SQLite, конфигурации и индекса. Проверить целостность;
   зашифрованную копию вынести с VPS. Приватный ключ расшифровки на VPS не класть.
6. Установить подготовленный путь nginx в существующий server monitor:8443;
   проверить конфигурацию до reload. Проверить HTTPS и закрытость без bridge
   ключа. DNS не менять. Установить `executionEnabled: true`, запустить API,
   индекс, dispatch и cleanup. Проверить чтение GitHub через ограниченный
   broker без запуска workflow. Снять `BRIDGE_MAINTENANCE` после проверок.
7. Проверить прежние пользовательские ключи, профиль, синхронизацию списка,
   обе календарные ссылки, подписки, старую и новую очередь, статус прогресса,
   основной и резервный адреса. Снять паузу прежнего исполнителя ХМАО.
   Наблюдать ближайшую обычную публикацию. Рассылки вручную не инициировать;
   проверка фактической штатной доставки — отдельное наблюдение её результата.

В этот момент состояние — «переключено, штатный цикл ожидает подтверждения».
После обычного цикла проверить данные на Pages, отчёт и отсутствие повторов.
Следующие территории и прямой DNS-переход рассматриваются отдельно.

## Возврат и аварийное восстановление

До снятия maintenance и первой новой записи можно вернуть прежнюю версию Worker
с исходным KV. После начала работы новой SQLite старый KV уже не актуален:
перенаправлять пользователей обратно на него нельзя.

После новых записей останавливают только новую API-службу и её служебные
таймеры, сохраняют свежую резервную копию, переключают `current` на предыдущий
совместимый пакет программы и снова запускают службы с **текущей SQLite и
текущим индексом**. Пользовательские данные и очередь назад не откатывают.
Переходник и внутренние ключи остаются теми же. Возврат в старый KV потребует
отдельного проверенного обратного переноса; здесь он не реализован.

При потере сервера восстанавливают зашифрованную копию на отдельной машине,
проверяют каждый файл и SQLite integrity, затем полноту профилей/подписок/
календарей и неопределённые задачи. Обычное копирование активного SQLite-файла
без WAL недопустимо: использовать online backup либо остановленные службы.
