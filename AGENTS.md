## Общая программа и установленная копия

- Единственный источник разработки — ветка `codex/program` репозитория
  `SelivanovAS/dashboard`. Новую работу вести в ветках `codex/*` от неё.
- `main` четырёх репозиториев — установленные региональные копии с рабочими
  данными. Наличие `.program-release.json` подтверждает управляемую установку;
  исходный коммит программы находится в этом паспорте и не равен обязательно
  текущему HEAD, поскольку данные продолжают обновляться.
- Общий код в установленных копиях не развивать и не синхронизировать merge
  между территориями. Выпускать точный пакет через `scripts/program_release.py`.
  Не переносить source-ветку целиком в `main`.
- В исходной ветке штатный CI собирает временные региональные деревья.
  Прежний полный pytest запускать в собранном дереве с привычными путями;
  источник не содержит рабочей картотеки и активных боевых workflows.
- До завершения перехода проверять паспорт конкретной территории. Отсутствие
  паспорта означает прежнюю установку, а не разрешение переписать её файлы.
- Профили четырёх территорий находятся в `deployment/regions/`. Секреты не
  включать в профили, пакеты, отчёты и журналы команд.
- Порядок сборки, публикации, проверки и отката:
  [общая программа](docs/Общая_программа.md).

## Как работать

- Общаться с пользователем по-русски, объяснять результат и последствия простыми
  словами. Пользователь — юрист банка. Пользовательские тексты и пояснения писать
  по-русски; идентификаторы, API-поля и соглашения существующего кода сохранять.
- Соблюдать системные инструкции и ограничения среды. В их пределах явный запрос
  пользователя задаёт объём работы и имеет приоритет над рекомендациями этого
  файла, исторических документов и skills.
- Запрос исправить проблему означает довести исправление до проверки. Не
  запрашивать повторно уже полученное разрешение. Уточнять только недостающие
  решения, которые существенно меняют результат; независимую работу продолжать.
- Перед правками проверить `git status`; сохранять посторонние изменения пользователя.
  Не выполнять попутную чистку, миграцию модели, данных или инфраструктуры.
- Сначала установить причину по затронутому коду, данным и логам. Документация и
  память помогают найти место, но не доказывают текущие настройки или работу прода.
  Начинать с `rg` и точечных чтений; не читать весь архив при каждой задаче.
- Skills применять по задаче. Их универсальные чеклисты не создают обязательного
  staging, внешних уведомлений, тикетов или мониторинга. Если инструкция вызывает
  остановку, назвать файл, процитировать правило и объяснить его применимость.
  Разрешения Claude из `.claude/` не являются разрешениями Codex.
- Независимые исследования и проверки можно делегировать; общие файлы не править
  параллельно без распределения ответственности. Тестировать соразмерно изменению;
  не повторять успешные проверки без новых изменений или обнаруженного риска.
- Существенную переделку UX сначала обосновать и согласовать по объёму. Обычное
  исправление в уже согласованной задаче не требует нового согласования.
- Рассылки другим людям выполнять только по явному поручению. Изменение расписания,
  исполнителя, деплой и публикацию выполнять в рамках разрешённого пользователем
  объёма; подготовка к ним сама по себе не означает разрешения на эти действия.

## Региональная изоляция

- Регион выбирается в `config.py`: env `REGION` → файл `REGION` в корне → `hmao`.
  Для Урала код региона — `sverdlovsk_yanao`. Значение `ural` используется как
  браузерный `STORAGE_NS`, а не как код региона Python.
- У каждого форка свои данные, отчёты, настройки и секреты. При синхронизации
  сохранять `REGION`, `region_front.js`, `manifest.json`,
  `cloudflare-worker/wrangler.toml`, `data/**` и территориальные отчёты `ops/**`.
  Не смешивать Worker/KV, URL, VAPID, localStorage и расписания территорий.
- Апелляционных судов может быть несколько: использовать `APPEAL_COURTS` и
  `appeal.court_domain`. Номер дела не уникален между судами: ключ включает суд;
  для bank-events — `домен|номер`. Учитывать площадку `srv_num`, где это требуется.
  При неоднозначной связке не выбирать первое совпадение по номеру; сохранять
  проверку суда и УИД, а случаи ручного импорта с неоднозначностью — для разбора.
- Часы заседания относятся к суду, а не к устройству юриста. Использовать
  `CourtConfig.timezone` с резервом на `RegionConfig.timezone`: у 6-го КСОЮ —
  `Europe/Samara` (UTC+4), у судов Башкортостана — UTC+5. В интерфейсе и дайджесте
  сохранять часы суда и подпись отличающегося пояса; календарь переводит событие
  с известным временем в UTC. Метки `updated_at` картотеки и отчёта здоровья
  записывать с явным смещением.
- Общий код переносить проверенным пакетом из `codex/program`, сверив паспорт
  и актуальный HEAD целевой территории. Историю и рабочие данные не переписывать.
- Исторический `merge=ours` не является механизмом выпуска. Пакет владеет
  только явно перечисленными файлами; `data/**`, территориальные отчёты и
  посторонние файлы сохраняются. На Урале трек «Иски банка» уже ведётся.
- Проверять форк в его собственном checkout с нужным регионом. Обновление shell-
  скрипта эталона не обновляет Python-код или конфиг регионального клона.

## Данные, парсеры и приём дел

- Схемы и поля `cases.json` не переименовывать без согласованной миграции читателей.
  Bank-данные загружать/сохранять через `load_bank_json` / `save_bank_json`, передавая
  полный документ: события хранятся отдельно, их нельзя потерять при сохранении.
  JSON — UTF-8 без BOM, CSV — UTF-8 с BOM. Сохранять УИД, историю и архивы.
- Не менять порядок инстанций полного прогона без разбора зависимостей:
  кассация → апелляция → первая инстанция. Поиск инстанции предшествует её карточкам;
  discovery/dedup и связки должны учитывать уже найденные дела.
- HTTP 200 не доказывает чтение карточки: защита, капча, заглушка и пустая оболочка
  не должны обновлять `last_checked_at`. Диагноз брать из результата конкретного
  запроса; не подменять причину отказа срабатыванием нашего предохранителя.
- Различать дефолт Python и эффективные настройки launcher. Полный прогон использует
  time-breaker, импорт — count-профиль 5/3. Не переносить настройки повторов и
  предохранителя между режимами без проверки; карточки проверять по реальному URL,
  а не только по скорости главной страницы суда.
- Иск, возвращённый / не принятый / переданный по подсудности до принятия,
  отсекается узким `fi_not_accepted_kind`. Не расширять его на прекращение и
  оставление без рассмотрения. Ручное добавление юристом имеет отдельные правила.
- При недоступной карточке иск против банка может заводиться незаполненным для
  дочитки; иск банка принимается по карточным правилам. Не уравнивать эти ветки
  ценой потери исков против банка или обхода фильтров истцового трека.
- Обычные повторные слоты VPS/Mac (`SKIP_CHECKED_TODAY=1` при smart-skip)
  не перечитывают успешно прочитанные сегодня карточки, включая материалы «М-».
  Поиск новых дел пропускается отдельно по источнику после сохранённого успеха
  за сегодня (`last_count > 0`, без `fail_streak`); неудачные чтения и нулевую
  выдачу не считать успехом. `--force` оболочки снимает дневной пропуск.
- При успешном чтении карточки на приёме `last_checked_at` и `intake_card_parse`
  ставятся вместе. Дочитка должна сохраняться на диск и не менять стадию дела,
  уже ушедшего в апелляцию. Проверку «дамп соответствует выбранному суду» сохранять.
- КСОЮ и президиум на сайте областного/верховного суда — разные источники.
  Открытые президиумы ищутся через `presidium_search.py`; `search_gated` /
  `search_disabled` сохраняют ручной путь. Не объявлять все президиумы закрытыми.
  Импорт КСОЮ проверяет территорию по выдаче и карточке; не обходить эту проверку
  ради добавления дела и не смешивать раздел президиума с апелляцией того же сайта.
  Свежесть дампов и ошибки карточек учитывать по домену и `delo_id`; импорт
  одной инстанции не подтверждает импорт другой. Неоднозначную старую отметку
  по домену не присваивать сразу обоим разделам.
- Ожидание кассационного текста ведёт `act_watch.py`, апелляционного —
  `appeal_act_watch.py`, первой инстанции — `fi_act_watch.py` независимо от стадии,
  нового круга и архива. Сохранять задачу и событие публикации до подтверждения
  контекста дайджеста; смена стадии не закрывает ожидание. Отсутствующая ссылка
  и несовпадение реквизитов должны быть видны в отчёте, а не считаться успехом.
- Первичная загрузка старого текста не создаёт новость. Для публикации нужен
  подтверждённый переход «текста нет → текст появился». Очереди выполняются
  после основного обхода: общий бюджет 600 секунд, историческая догрузка не более
  10 карточек / 180 секунд в день. Ритм 0–30 дней — рабочие дни, 31–90 — неделя,
  91–180 — месяц, затем ожидание завершается без архивации дела. Правила и даты —
  [контракт публикаций 06.10](docs/Публикации_актов_2026-10-06.md).
- Реализация 07.10 сохраняет найденных кандидатов в `discovery_queue`
  до карточных попыток и лимитов. Откат parse-транзакции сохраняет только
  проверенную очередь своей территории. Независимым задачам зарезервированы
  90 секунд внутри общего дедлайна; 100% основной очереди не является гейтом
  исторической догрузки. Исходный снимок старых FI-текстов и ИЛ не создаёт новость.
  Контроль ИЛ по требованиям банка не нужен третьим лицам и при полном отказе;
  смена основания требует проверки, старую расчётную силу не переносить.
  Режим `--retry-only` не меняет доставленный контекст: события идут
  в `pending_retry_context` до следующего обычного выпуска. Новые таймеры
  12:00/16:00 устанавливаются отдельно от Git. Результаты установки и
  границы проверки — в [отчёте выпуска](docs/Выпуск_парсинга_2026-10-07.md).
- Архивная страховочная проверка решённых FI-дел и процессуально завершённые
  дела без незавершённой жалобы проверяются раз в 7 дней. Будущие заседания
  обоих треков сохраняют прежние правила. `fi_act_checked_at` и
  `writ_checked_at` не заменяют `last_checked_at`: дочитка только текста или
  листов не должна откладывать полноценную проверку жалоб и движения дела.
  HTML карточки переиспользуется только внутри одного прогона по полному URL.
  Отрицательный кэш вспомогательного поиска апеллянта действует до следующего
  дня только при распознанном «нет данных»; ошибки и общий поиск не кэшируются
  по этому правилу.
- Дедуп актов (`.digested_acts`, `.cassation_acts`) и однократное объявление новых
  импортированных дел сохранять. Не менять эмпирические параметры 7kas
  (`delo_table=g33_case`, `new=2800001`) без проверки настоящей выдачи/карточки.
- Для очередей и полноты обхода указывать дату снимка, регион, инстанцию и причины
  пропуска. Недоступные карточки остаются в полном запланированном знаменателе.

## Запуски, импорты и доставка

Ниже — схема, подтверждённая файлами репозитория, а не проверка живых таймеров.

- Основной исполнитель — `ops/vps-run/`, использующий общую реализацию
  `ops/mac-local-run/`; Mac — ручной резерв. С 01.10.2026 его LaunchAgents
  парсинга и импорта отключены через `launchctl disable` и выгружены.
  Не включать их при обычной синхронизации кода: перевод исполнителя требует
  остановки писателей VPS и отдельного поручения. Локальный `.run.lock`
  не защищает от одновременной работы другого хоста.
  В эталонном `wrangler.toml` сейчас
  задан отдельный cron профилей `17 21 * * *`,
  `PROFILE_CLEANUP_ENABLED = "1"`, `CRON_UTC = ""`, `IMPORT_EXECUTOR = "vps"`.
  Выкладка и настройки трёх Workers проверены 15.09.2026; состав и границы —
  в [отчёте выпуска](docs/Выпуск_очистки_профилей_2026-09-15.md). `update_cases.yml`
  сохраняет полный ручной/аварийный запуск. Не включать два одновременных писателя.
- Прогресс VPS/Mac отправляется в KV раз в 300 секунд; полный пакет из
  40 строк и финальный статус отправляются сразу. GitHub-отправитель отдельный,
  его дефолт — 60 секунд. Суточный бюджет KV общий для территорий; не уменьшать
  интервалы ради отладки без оценки расхода. Доказательства и оценка экономии —
  в [аудите KV](docs/Аудит_KV_2026-10-01.md).
- Утренние слоты VPS — будни 06:00–08:30 каждые полчаса и 08:45 по Екатеринбургу.
  Доставка разрешена с 08:45 либо с `--force`; доля прочитанных карточек влияет
  на отчёт, а не разрешает раннюю отправку. `--force` обходит дневной гейт.
- С 13.09.2026 на VPS парсинг, импорт и доставка — отдельные службы. При
  `CM_IMPORTS_AFTER_PARSE=0` утренний драйвер не ждёт импорты; их запускает systemd
  после завершения службы парсинга, в том числе с ошибкой. Mac-резерв сохраняет
  импорт внутри драйвера. `court-delivery.timer` проверяет готовность с 08:45:
  каждые 5 минут до 10:00, затем каждые 15 минут до 23:45 по будням.
  `--can-deliver` допускает и завершённый сегодняшний прогон без новых событий.
  Доставка использует тот же `.run.lock` и журнал транзакций; занятый клон ждёт
  следующей попытки. Подробности — в [рантбуке VPS](ops/vps-run/README.md).
- Сначала публикуются данные, затем отдельной транзакцией фиксируется доставка.
  Сохранять журнал доставки, проверку удалённого результата при неопределённом
  push и связь маркера коммита `(Mac-парсинг)` с `replay_on_push.yml`, в том числе
  на VPS. Список публикуемых данных брать из `ops/stage_data_files.sh`.
- Replay собирает дайджест и Telegram, публикует данные и перед Web Push пытается
  дождаться актуального содержимого Pages (до ~7 минут). При таймауте или неудачном
  rebase текущий workflow допускает push без подтверждения публикации. Менять
  `DEFER_WEB_PUSH` и отдельный push-шаг согласованно; не создавать вторую рассылку
  из VPS/Mac.
- Код технических отчётов заменяет личный Telegram-дайджест итогом парсинга,
  публикации и push; явно выбранная группа сохраняет текст дайджеста. Не выводить
  успешную доставку из `delivered_at` или общего статуса Actions. Модель пересказа,
  кэш и причины резервов брать из аудита фактических попыток. Контракт и граница
  установки — [технические отчёты](docs/Технические_отчёты.md).
- `--json`, `--replay-last`, импорт, `wrangler deploy` и Run workflow — операции
  с данными/сетью/доставкой, не команды обычной проверки. `test_digest.yml` даже с
  `commit_results=false` отправляет Telegram. Для теста без доставки использовать
  изолированные данные, временный кэш и заглушки транспорта.
- Дампы и точечные пачки идут в очередь VPS. Пятиминутный поллер `import:pending`
  работает круглосуточно ежедневно; ежедневные слоты каждый час с 12:00 до 20:00 и импорт после парсинга
  страхуют неудачи. Общий `.run.lock` клона сериализует парсинг и импорт; занятый
  lock не означает, что отметка нового импорта обработана.
- Полная очередь приходит из `/admin/import-log?include_queue=1`, поле `queue`;
  `items` — только последние 50 записей истории. Статусы формы отслеживать по UUID,
  не связывая завершение старого задания с текущим вводом. После подтверждённого
  приёма форма освобождается; дампы в браузерном хранилище не сохранять.
- Шлюз импортов — общий модуль Worker, но `IMPORT_GATEWAY_ORIGIN` задаётся своей
  территорией; без него этот способ загрузки выключен. Сохранять проверки адреса,
  формата отдельного токена загрузки, размера, SHA-256 и выбранного суда до
  записи в KV. Контракт — в
  [документации Worker](docs/technical/09-cloudflare-worker.md#загрузка-дампа-через-шлюз-территории).
- Терминальные ошибки входных данных повторно не гонять; сетевые ошибки допускают
  повтор. Слоты `IMPORT_SLOTS_LOCAL` и systemd менять согласованно. При изменении
  парсерного cron держать вместе `[triggers].crons` и `CRON_UTC`, а выкладку
  проверять отдельно. Служебный cron профилей не включает парсер и не меняет
  `CRON_UTC`; `scheduled` обязан завершить его ветку до dispatch.
- Профили: 7 дней без использования для пустого без push/календаря, 30 дней
  для остальных без push, затем 7 дней восстановления. Действующая запись
  связанной push-подписки защищает профиль. Активность устройства и календаря
  хранить отдельно от watchlist/LWW, не чаще записи за сутки; административное
  чтение и канонизация её не продлевают. У старых профилей отсчёт начинается
  с включения учёта, не с `created_at`/`updated_at`. Очистка требует полного
  списка push, повторной проверки перед удалением и защитной паузы KV после
  закрытия восстановления. Контракт — в
  [документации Worker](docs/technical/09-cloudflare-worker.md#очистка-неактивных-профилей-15092026).

## LLM и формат дайджеста

- Codex — агент разработки; GPT-6 Astra в Codex не меняет LLM дашборда.
  В дашборде поддержаны **Claude**, GigaChat и OpenRouter. `ANTHROPIC_API_KEY`
  и `CLAUDE_MODEL` относятся к Claude. Прямого провайдера OpenAI в текущем коде нет.
- Python без env использует `LLM_PROVIDER=openrouter`; `update_cases.yml` и
  `replay_on_push.yml` по умолчанию задают `openrouter`, если нет override в
  Actions Variables. `test_digest.yml` по умолчанию использует `claude`.
  Не выдавать эти дефолты за проверенные значения production Variables.
- Боевой путь — программный шаблон событий + LLM-пересказ мотивировок актов.
  Полный LLM-дайджест включается отдельно через `DIGEST_FULL_LLM=1`.
  Сохранять настроенные промпты; существенную смену формата заранее объяснять.
- Кэш пересказов зависит от провайдера/модели и для неэталонного Claude — от effort;
  старые haiku-ключи сохраняются. Сначала проверяется кэш, затем ключ провайдера.
  Без ключа — пропуск, не выдуманный сбой и не сырой акт под видом AI-анализа.
- С 06.10.2026 локальный пересказ использует закреплённый Apodex через OpenRouter,
  затем GigaChat 3 Pro, затем Claude Haiku 4.5 (`LLM_SUMMARY_PROVIDER_FALLBACK=1`). Случайного
  `openrouter/free` в этой цепочке нет. Это не доказательство выкладки.
- Всем моделям передаётся один полный подготовленный акт; неизвестный или малый
  контекст пропускает модель, не отрезает текст. Один смысловой отказ допускает
  одну проверку достаточности; повторный отказ не запускает поиск согласной модели.
- `.act_summaries.pending.json` отделена от дедупа уведомлений. Повтор обновляет
  анализ без нового события; дочитка старого источника не объявляет акт повторно.
  Сохранять фактического автора ответа, аудит источника и bank-events. Контракт —
  [документация LLM](docs/technical/06-дайджесты-и-llm.md).
- Replay должен обновлять анализ обоих треков и сохранять bank-events; LLM-алерты
  есть и в полном прогоне, и в replay. Не опираться на старое обратное утверждение.
- Порядок юридических блоков: ИЛ → решения → иные события → заседания → новые иски.
  Telegram HTML: `<b>`, `<i>`, `<a href>`; сохранять разбиение по лимиту сообщения,
  сокращение сторон без потери соответчиков и проверки линтера дайджеста.

## Проверка и выпуск

- Для правки документации проверить факты, локальные ссылки и `git diff --check`.
  Полный pytest для неё не нужен. Для кода запустить затронутые проверки; полный
  suite — при изменении общих механизмов, риске межмодульных регрессий или явном
  требовании выпуска. Для локальных правок достаточно затронутых проверок и
  предусмотренного проектом CI.
- Оба каталога тестов включены в `pytest.ini`; команда из корня:
  `python3 -m pytest`. Выбирать рабочее Python-окружение с зависимостями проекта;
  GitHub CI использует Python 3.12. Проверки без зависимости могут быть пропущены:
  не называть skipped успешной проверкой поведения.
- Ссылки на функции здесь даны без номеров строк. `refresh_doc_anchors.py`
  обрабатывает `docs/technical/*.md` и `CLAUDE.md`, но не `AGENTS.md`.
  После смещения кода проверить `python3 scripts/refresh_doc_anchors.py`;
  `--write` применять при необходимости и просматривать diff. Страж:
  `python3 -m pytest scripts/tests/test_doc_anchors.py -q`.
- После изменения `admin_page.js` рендерить owner/operator HTML и разбирать каждый
  вложенный `<script>` через `vm.Script`. Есть проверка:
  `python3 -m pytest scripts/tests/test_admin_pult.py::test_admin_page_inner_js_parses -q`.
  Она требует Node; одного `node --check` внешнего файла недостаточно.
- UI проверять на узком экране, реальном масштабе данных и затронутых ролях;
  смотреть консоль и результат в браузере. Для `app.js` / `styles.css` обновлять
  `?v=N` в `sberbank_dashboard.html` и `CACHE_VERSION` в `service-worker.js`.
  Неверсионированный `DATA_CACHE` сохранять: выпуск кода не должен стирать офлайн-данные.
- Коммиты — с кратким русским описанием; предпочтителен принятый формат с эмодзи.
  Стадировать конкретные файлы задачи, не включать секреты и чужие изменения.
  Опубликованные коммиты не amend/rebase; создавать новые.
- Поручение «комить, пуш и синк Урала» включает commit/push эталона, проверенный
  выпуск пакета на Урал, проверки региона и итогового расхождения. Повторное разрешение
  на уже порученные шаги не нужно. Отдельный деплой выполнять, когда он входит
  в поручение; для Worker проверить нужные территории и их собственные конфиги.
- Локальные тесты, CI, push и deploy — разные результаты. В ответе назвать только
  фактически выполненные проверки, оставшиеся ограничения и состояние выпуска.
