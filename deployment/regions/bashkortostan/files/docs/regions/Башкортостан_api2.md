# Дополнительный вход api2 для Башкортостана

Первоначальная настройка — 12.09.2026; маршрут загрузки обновлён 15.10.2026. Адрес `https://api2-bashkortostan.delosud.ru`
создан по запросу владельца по схеме существующих шлюзов ХМАО и Урала.
Это дополнительный вход к тому же Worker и KV Башкортостана. Ключи владельца
и оператора прежние; ссылки с ключами хранятся вне Git в отдельных файлах
`owner-access-api2.txt` и `operator-access-api2.txt`.

## Устройство

- DNS: A → `195.19.66.234`, DNS only, TTL 300 секунд.
- VPS: отдельный `/etc/nginx/sites-available/delosud-gw-bashkortostan`,
  символьная ссылка в `sites-enabled`; [копия конфигурации](../../ops/vps-run/api2-bashkortostan.nginx.conf).
- Внешний HTTPS проксируется в `api-bashkortostan.delosud.ru`, с проверкой
  сертификата upstream, правильными Host/SNI и сохранением методов, тела,
  заголовков и query. Лимит nginx — 10 МиБ.
- Отдельный сертификат Let's Encrypt действует до 11.12.2026. Продление
  через существующий `certbot.timer`, webroot `/var/www/letsencrypt-bashkortostan`
  и hook `systemctl reload nginx`. HTTP перенаправляется на HTTPS;
  путь ACME остаётся доступным для продления.
- В access-log нового виртуального сервера записывается URI без query,
  чтобы не включать ключи ссылок в обычный журнал обращений.
- Конфигурация прежних шлюзов сохранилась побайтно. Их защищённые `/admin`
  после включения нового виртуального сервера отвечали штатным 401 без ключа.

Worker, расписание, данные и адреса автоматических исполнителей не менялись.
`api2` не добавлялся в автоматические fallback-адреса дашборда: это такой же
отдельный вход по ссылке, как существующие api2 ХМАО и Урала. Имя оператора
и его настройки интерфейса на новом origin нужно указать при первом входе;
серверная очередь и картотеки общие с основным адресом Башкортостана.

## Живые проверки

`nginx -t` прошёл, конфигурация применена через reload. DNS и действительный
HTTPS проверены с внешней машины. Владелец и оператор получают полноценный
HTML (около 358 КБ), содержащий ссылки на данные новой территории. Неверный
ключ получает 401, операторский `/admin/data` — 403. Журнал импорта и список
GitHub-запусков доступны с операторским ключом. CORS preflight возвращает 204
с разрешённым origin дашборда.

## Передача дампов: исправление 15.10.2026

Прямой большой POST с VPS в Cloudflare обрывался до ответа Worker. 15.10
живой nginx зарегистрировал семь 502 на `/admin/import-dump`. Безопасная
проба с пустым `court_domain` воспроизвела разницу: JSON 32 байта вернул
ожидаемый 400, JSON 150 032 байта — 502 через 15 секунд. Это ошибка транспорта,
а не проверки выбранного суда или разбора карточек.

Два пути nginx направляются в отдельную службу на `127.0.0.1:8786`:

- `/admin/import-dump` принимает исходный JSON после проверки роли в Worker;
- `/_gateway-upload/` отдаёт его Worker по отдельному временному токену.

Служба передаёт в существующий Worker только описание загрузки, её размер и
SHA-256. Worker забирает исходные байты, сверяет контрольную сумму и выполняет
прежнюю валидацию и постановку в очередь. Nginx сжимает ответ загрузки gzip;
это существенно для маршрута VPS → Cloudflare. Тело хранится только в памяти
до ответа (TTL 75 секунд), лимит транспортного JSON 10 МиБ. Worker сохраняет
прежний предел HTML 2 МиБ символов. Не повторять POST автоматически при
неопределённом результате: сначала проверить журнал по UUID.

Файлы инфраструктуры включены в профиль Башкортостана:

- `ops/vps-run/bashkortostan_upload_relay.py`;
- `ops/vps-run/court-monitor-upload-bashkortostan.service`;
- `ops/vps-run/api2-bashkortostan.nginx.conf`.

Размещение службы: `/opt/court-monitor-upload-bashkortostan/`; systemd-unit —
`/etc/systemd/system/court-monitor-upload-bashkortostan.service`. Устанавливать
копии из проверенного пакета, предварительно сохранив старые файлы. Проверять
Python, `systemd-analyze verify` и `nginx -t`, запускать службу перед reload
nginx; после успешной сетевой проверки включить автозапуск. При откате
восстановить прежний nginx, проверить и перечитать конфигурацию, затем вернуть
скрипт/unit и прежнее состояние службы. Откат возвращает известное ограничение
больших прямых POST.

Worker, KV, расписания и рабочие Git-клоны этим инфраструктурным исправлением
не заменяются. `/admin/add-case` и остальные пути сохраняют прежний маршрут.
Не перевыпускать сертификаты других территорий.

### Проверки и границы

Контракт службы проверяется существующим интеграционным набором:
`RELAY_PATH=deployment/regions/bashkortostan/files/ops/vps-run/bashkortostan_upload_relay.py python3 scripts/tests/test_tyumen_upload_relay.py`.
В собранном дереве используется `RELAY_PATH=ops/vps-run/bashkortostan_upload_relay.py`.
Отдельный pytest-тест запускает этот набор для профиля Башкортостана.

После переключения безопасные запросы с текстом 281 283, 768 033 и 1 966 113
байт вернули ожидаемый 400 и правильный `X-Import-Gateway-SHA256`: тело
получено полностью, но пустой домен намеренно не позволяет создать импорт.
Настоящие выдачи Кировского районного суда по одному делу и по 25 делам также
прошли эту проверку (83 451 и 117 850 байт JSON). Контрольный импорт настоящей страницы по существующему делу № 2-5920/2026:
15.10.2026 в 18:29:03 (Уфа/Екатеринбург) получены HTTP 200 и правильный SHA-256,
UUID `14a02cdf-f20e-4022-b1ea-7ef3f7ad832b`. Плановый поллер 18:30 взял запись;
в 18:30:46 статус стал `done`, `rows=1`, `already=1`, `added=0`, ошибок нет.
Полная очередь пуста; SHA-256 `cases.json` и `cases_bank.json` до и после совпал.
Это подтверждает передачу, приём и обычную обработку реального дампа; добавление
нового дела этим тестом не проверялось.

Граница проверки: искусственный плохо сжимаемый JSON 150 032 байта вызвал
таймаут обратного скачивания (20 секунд). Исправление подтверждает загрузку
проверенных судебных HTML, но не устраняет все ограничения внешнего сетевого
маршрута и не гарантирует передачу любого содержимого до формального лимита.
При такой ошибке служба возвращает пояснение; проверять журнал перед повтором.

В журналах службы остаются только событие, статус, размер, длительность и тип
исключения. Тела, ключ роли и токен загрузки не записываются. На путях загрузки
access-log отключён; error-log nginx ограничен `crit`, поскольку обычные
upstream-ошибки включают query с ключом роли.
