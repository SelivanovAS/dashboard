# Мониторинг судебных дел ПАО Сбербанк

Автоматизированная система мониторинга гражданских дел с участием ПАО Сбербанк по трём инстанциям ХМАО-Югры:
- 1-я инстанция — 20 районных/городских судов ХМАО-Югры,
- апелляция — Суд ХМАО-Югры (oblsud--hmao.sudrf.ru),
- кассация — 7-й кассационный суд общей юрисдикции (7kas.sudrf.ru, фильтр по 1-й инст. ХМАО).

Включает веб-дашборд для анализа дел, Python-скрипт для сбора данных, AI-дайджесты судебных актов и уведомления в Telegram + PWA push.

**Дашборд:** [selivanovas.github.io/dashboard](https://selivanovas.github.io/dashboard/sberbank_dashboard.html)

> 📚 **Подробная техническая документация** — [`docs/technical/`](docs/technical/README.md):
> архитектура, модель данных, жизненный цикл дела, парсеры, конвейер, дайджест,
> доставка, фронтенд, Cloudflare Worker, CI/CD и рантбук.

## Возможности

- **Автоматический сбор данных** — ежедневный парсинг 22 источников (20 судов 1-й инст. ХМАО + Суд ХМАО-Югры (апелляция) + 7-й кассационный суд)
- **Интерактивный дашборд** — таблица дел с фильтрами, поиском и сортировкой
- **AI-дайджесты** — автоматическое резюмирование судебных актов через Claude API
- **Telegram-уведомления** — отправка дайджестов в чат
- **Аналитика** — статистика по ролям, исходам, категориям дел
- **Расписание заседаний** — блок ближайших заседаний с датами и временем
- **Отслеживание новых дел** — уведомление о появлении новых дел с момента последнего визита
- **Адаптивный дизайн** — десктоп (таблица) и мобильная версия (карточки)
- **Админка** — страница на Cloudflare Worker: запуск прогонов в два клика (полный / стандартный со smart-skip), **живой лог прогона** со свёрткой по фазам (виден и после завершения), статусы GitHub Actions, здоровье парсеров, управление push-подписчиками и их watchlist'ами

## Стек технологий

### Фронтенд
- HTML5 / CSS3 / Vanilla JavaScript (single-page, без фреймворков)
- Шрифты: Literata, Source Sans 3, JetBrains Mono
- localStorage для хранения настроек и отслеживания новых дел

### Бэкенд
- Python 3.12
- `requests` — HTTP-запросы к сайту суда
- `html.parser` — парсинг HTML-таблиц
- Anthropic Claude API — генерация дайджестов
- Telegram Bot API — отправка уведомлений

### Инфраструктура
- Cloudflare Workers — cron-триггер автоматизации, хранилище push-подписок (KV), админка с живым логом прогона
- GitHub Actions — выполнение workflow (парсинг, дайджест, коммит)
- GitHub Pages — хостинг дашборда
- JSON (`data/cases.json` + архивы) — хранение данных о делах; legacy CSV коммитится для совместимости

## Дашборд

Одностраничное веб-приложение, открываемое напрямую в браузере. Загружает CSV-данные из Google Sheets или напрямую из репозитория.

### Основные разделы

| Раздел | Описание |
|--------|----------|
| **Статистика** | 4 карточки KPI: всего дел, в производстве, процент выигрышей, опубликованных актов |
| **Чипы** | Разбивка по ролям (истец/ответчик/третье лицо) и результатам (оставлено/отменено/изменено) |
| **Ближайшие заседания** | До 10 ближайших заседаний с датой, временем, номером дела и сторонами |
| **Поиск и фильтры** | Полнотекстовый поиск, фильтры по статусу, роли банка и категории |
| **Таблица дел** | Сортируемая таблица с раскрывающимися строками и цветовыми бейджами |
| **Мобильные карточки** | Адаптивный вид для экранов < 768px |

### Фильтрация

- **Статус:** В производстве, Назначено, Отложено, Приостановлено, Решено, Архив (30+ дней)
- **Роль банка:** Истец, Ответчик, Третье лицо
- **Категория:** Динамически формируется из данных
- **Поиск:** По номеру дела, сторонам, категории, суду, событиям, заметкам

### Настройка источника данных

При первом открытии дашборд предлагает:
1. Подключить Google Sheets с CSV-данными (URL сохраняется в localStorage)
2. Загрузить демо-данные для ознакомления

## Бэкенд-автоматизация

Скрипт `scripts/update_cases.py` (тонкий CLI-фасад пакета `scripts/court_monitor/`) выполняет полный цикл обновления:

```
22 источника (суды) → Парсинг → cases.json (+ legacy CSV) → State machine стадий → AI-дайджест → Telegram + PWA push → Git commit
```

### Этапы работы (`--json`, фазы 1-9 в логе прогона)

1. **Загрузка данных** — `cases.json`, миграция стадий, дедупликация
2. **Поиск новых дел** — апелляция (поиск по «Сбербанк») и 20 судов 1-й инстанции
3. **Обновление карточек активных дел** — какая карточка парсится, решает стадия дела (1-я инст. / апелляция / кассация): события, статусы, публикация актов, мотивировки, признаки жалоб
4. **Кассация 7kas** — поиск, привязка карточек, discovery дел, пришедших сразу с кассации
5. **Здоровье парсеров** — детектор «молчаливой поломки» (суд, стабильно дававший результаты, вернул 0 → 🩺-алерт)
6. **Связка и state machine** — переходы стадий, архивирование, реактивация
7. **Гибридный дайджест** — события рендерит код, Claude (Haiku) пересказывает только мотивировки актов
8. **Доставка** — Telegram (с разбиением до 4096 символов) + PWA push с персонализацией по watchlist
9. **Коммит данных** — обновлённые файлы уходят в репозиторий

### Особенности

- Фильтрация дел Сбербанк Страхование (дочерняя компания) — исключаются из мониторинга
- Вежливый парсинг — задержка 2–3 секунды между запросами
- Жизненный цикл дела — семь стадий от 1-й инстанции до кассации с автоархивированием по тайм-аутам и реактивацией при поздней жалобе ([docs/technical/03](docs/technical/03-жизненный-цикл-дела.md))
- Дедупликация дайджестов через файл `.digested_acts`
- Smart-skip (`SKIP_NON_WORKING_DAYS=1`) — пропуск нерабочих дней РФ и дел с известной будущей датой

## Схема данных

Источник истины — `data/cases.json` (стадии, история раундов, блоки трёх инстанций; полная схема — [docs/technical/02](docs/technical/02-модель-данных.md)). Ниже — схема **legacy CSV** (`data/sberbank_cases.csv` + архивный), который по-прежнему коммитится для совместимости — 20 колонок:

| Колонка | Тип | Описание |
|---------|-----|----------|
| Номер дела | Строка | Номер дела, напр. `33-2957/2026` |
| Дата поступления | Дата | Дата поступления в суд (ДД.ММ.ГГГГ) |
| Истец | Строка | ФИО / наименование истца |
| Ответчик | Строка | ФИО / наименование ответчика |
| Категория | Строка | Иерархическая категория дела (через `→`) |
| Суд 1 инстанции | Строка | Суд первой инстанции |
| Роль банка | Перечисление | `Истец` / `Ответчик` / `Третье лицо` |
| Статус | Перечисление | `В производстве` / `Решено` |
| Последнее событие | Строка | Текст последнего процессуального события |
| Дата события | Дата | Дата последнего события |
| Время заседания | Время | Время заседания (ЧЧ:ММ) |
| Акт опубликован | Перечисление | `Да` / `Нет` |
| Результат | Строка | Текст результата рассмотрения |
| Ссылка | Строка | `case_id\|case_uid` для ссылки на сайт суда |
| Заметки | Строка | Дополнительные заметки (ручной ввод через Google Sheets) |
| Апеллянт | Строка | Кто подал апелляцию (`Банк` / `Иное лицо`) |
| Дата публикации акта | Дата | Дата публикации судебного акта |

### Архивирование

Скрипт `update_cases.py` автоматически переносит дела со статусом `Решено` и датой события более 30 дней назад в `data/sberbank_cases_archive.csv`. Это удерживает основной CSV компактным. Дашборд прозрачно подгружает оба файла и склеивает их (с дедупликацией по номеру дела) — пользователь видит полную историю.

**Ротация JSON-архива по годам.** Чтобы вес приложения (PWA) не рос безгранично по мере накопления дел, архив разделён на «горячий» и «холодный». `data/cases_archive.json` («горячий») содержит только дела, заархивированные за последние 12 месяцев (`COLD_ARCHIVE_DAYS=365`) — именно его подгружает фронт. Дела старше года автоматически выносятся в «холодные» годовые файлы `data/cases_archive_YYYY.json`, которые фронт **не загружает**, но скрипт читает их в индекс дедупликации (чтобы старое дело не всплыло как «новое»). Размен: дела старше года не отображаются во вкладке «Архив» на дашборде, но сохраняются в репозитории. Холодные дела «заморожены» — при возобновлении возвращаются вручную (`add_cases_manually.py`).

## Автоматизация

### Cloudflare Worker (триггер + админка)

GitHub Actions cron ненадёжен на бесплатных планах (задержки до 3-4 часов). Поэтому запуск workflow выполняется через Cloudflare Worker, который вызывает GitHub API `workflow_dispatch` точно по расписанию. Тот же Worker хранит push-подписки (KV) и отдаёт админку.

- **Worker:** `court-monitor-trigger` (`cloudflare-worker/`)
- **Расписание:** будни 3:45 UTC (6:45 МСК, `crons = ["45 3 * * mon-fri"]`); выходные и праздники РФ дополнительно отсекает `isHoliday()`. Плановый прогон идёт со `smart_skip=true`.
- **Секреты:** `GITHUB_PAT` (GitHub API), `OWNER_SECRET` (админка), `PUSH_SECRET`, `PROGRESS_SECRET` (живой лог), `VAPID_PRIVATE_KEY` (тест-push)

Изменить расписание можно:
1. В файле `cloudflare-worker/wrangler.toml` → `crons = [...]` → `npx wrangler deploy`
2. В Cloudflare Dashboard → Workers → court-monitor-trigger → Settings → Triggers

### Админка

`https://court-monitor-trigger.<аккаунт>.workers.dev/admin?secret=<OWNER_SECRET>` — открывается в браузере, в том числе с телефона. Подробно — [docs/technical/09](docs/technical/09-cloudflare-worker.md).

- **Запуск прогонов:** кнопка «▶ Полный прогон» (`smart_skip=false` — парсит всё) и «Стандартный прогон» (`smart_skip=true` — как ежедневный автозапуск; в нерабочий день сразу завершится пропуском). Рядом — мини-форма теста дайджеста с выбором LLM-провайдера.
- **Живой лог прогона:** основной workflow гонит свой stdout через pass-through-пушер `scripts/gh_progress_pusher.py` → `POST /run-progress` → блок «Прогон (GitHub Actions)» обновляется каждые 5 с. Лог свёрнут по фазам «[1/9]…[9/9]» (текущая фаза раскрыта, бейджи ⚠/✖ по WARNING/ERROR, итоговая сводка видна сразу), хранится 14 дней (текущий + предыдущий прогон) — можно смотреть и после завершения. Тот же блок показывает Mac-резерв.
- **Мониторинг:** последние прогоны GitHub Actions со статусами, здоровье парсеров со спарклайнами, данные последнего дайджеста.
- **Подписчики:** список push-подписок с именами и watchlist'ами, тест-push, удаление.

### GitHub Actions

#### 📊 Основной прогон: парсинг + дайджест (`update_cases.yml`)

- **Триггер:** `workflow_dispatch` (Worker-cron по будням, кнопки в админке или GitHub UI)
- **Действия:** Парсинг 22 источников → обновление `cases.json` (+ legacy CSV) → state machine стадий и архив → гибридный дайджест (события рендерит код, Claude пересказывает мотивировки актов) → Telegram + PWA push → коммит в репозиторий. Stdout прогона параллельно уходит в живой лог админки.
- **Галки:**
  - `to_group` — слать в корпоративную группу (по умолчанию — личный чат).
  - `smart_skip` — пропуск нерабочих дней РФ и дел с известной будущей датой (cron передаёт `true`).

#### 🧪 Тест дайджеста (`test_digest.yml`)

- **Триггер:** Только ручной запуск (`workflow_dispatch`)
- **Действия:** Replay последнего сохранённого контекста (`data/last_digest_context.json`) через LLM с актуальным промптом → Telegram → PWA push → коммит свежего `data/last_digest.json`.
- **Галки:**
  - `to_group` — слать в корпоративную группу (по умолчанию — личный чат).
  - `push_all` — PWA push на все устройства (по умолчанию — только владельцу).
  - `full_llm` — старый полный LLM-вызов вместо гибрида (`DIGEST_FULL_LLM=1`).
  - `llm_provider` — LLM-провайдер: `claude` (по умолчанию) / `gigachat` / `openrouter`.
  - `gigachat_model` — выпадающий список моделей GigaChat: GigaChat-2-Pro (дефолт) / GigaChat-2 / GigaChat-2-Max.
  - `openrouter_model` — выпадающий список мест в рейтинге бесплатных моделей shir-man.com: «модель дня (топ-1)» (дефолт) … «топ-5»; конкретная модель подставляется на прогоне из свежего рейтинга.
  - `llm_model` — другая модель текстом, перебивает оба списка.
  - `commit_results` — опубликовать результаты (дайджест попадёт на дашборд + уйдёт PWA push). По умолчанию выключена — только Telegram, без пуша и без изменений на сайте.

## Переменные окружения

| Переменная | Описание | Где используется |
|------------|----------|------------------|
| `ANTHROPIC_API_KEY` | API-ключ Anthropic (Claude) | Генерация дайджестов |
| `GIGACHAT_AUTH_KEY` (+ `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`) | GigaChat — альтернативный LLM (`LLM_PROVIDER=gigachat`) | Тест дайджеста |
| `OPENROUTER_API_KEY` (+ `OPENROUTER_MODEL`) | OpenRouter — третий LLM (`LLM_PROVIDER=openrouter`); пустая модель = «модель дня» | Тест дайджеста |
| `TELEGRAM_BOT_TOKEN` | Токен Telegram-бота | Отправка уведомлений |
| `TELEGRAM_CHAT_ID` | ID корпоративной группы (используется при `to_group=true`) | Отправка уведомлений |
| `TELEGRAM_CHAT_ID_TEST` | Личный чат — дефолтный получатель дайджеста | Отправка уведомлений |
| `PUSH_WORKER_URL`, `PUSH_SECRET`, `VAPID_PRIVATE_KEY` | Web Push для PWA через Worker | PWA-уведомления |
| `PROGRESS_URL`, `PROGRESS_TOKEN` | Живой лог прогона в админку (`gh_progress_pusher.py`); workflow собирает их из `PUSH_WORKER_URL` и `PUSH_SECRET \|\| PROGRESS_SECRET` — без них пушер работает как cat (и говорит об этом одной строкой в логе рана; первый сбой POST — одна ⚠️-строка с HTTP-кодом) | Живой лог |
| `SKIP_NON_WORKING_DAYS` | `1` = smart-skip (нерабочие дни + дела с будущей датой) | Скрипт обновления |
| `LOG_LEVEL` | Уровень логов прогона (`DEBUG`/`INFO`/…, дефолт `INFO`) | Скрипт обновления |
| `DIGEST_FULL_LLM` | `1` = откат на полный LLM-дайджест вместо гибрида | Дайджест |
| `CSV_PATH`, `CSV_ARCHIVE_PATH` | Пути к legacy CSV (дефолты в `data/`) | Скрипт обновления |
| `DIGESTED_ACTS_PATH` | Путь к файлу обработанных актов | Скрипт обновления |

В GitHub Actions переменные задаются через **Settings → Secrets and variables → Actions**.
