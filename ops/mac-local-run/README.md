# Общие скрипты VPS и резервного запуска на Mac

Основной исполнитель — VPS, использующий скрипты из этого каталога через
[Linux-обёртки](../vps-run/README.md). Mac остаётся резервом. Ниже описаны
текущие файлы репозитория, сверенные 13.09.2026; загруженность LaunchAgents,
установленные службы VPS, секреты и доступность судов проверяются отдельно.

Список территорий задаётся на каждой машине. Код поддерживает ХМАО, Урал и
Башкортостан. В [отчёте внедрения Башкортостана](../../docs/regions/Башкортостан_внедрение_2026-09-11.md)
зафиксированы третий клон VPS и подготовленный ручной резерв Mac; Башкортостан
тогда был исключён из автоматического списка Mac. Наличие клона само по себе
не включает его в расписание.

## Схема парсинга и доставки

`parse_all.sh` читает список клонов, готовит маршруты судов на Mac и запускает
`parse_and_push.sh` отдельно для каждого региона. В параллельном режиме Урал
(`sverdlovsk_yanao`) идёт первым, остальные — в порядке списка с интервалом
600 секунд. Для списка Урал → ХМАО → Башкортостан это старты через 0/10/20 минут.
Маршруты меняет родитель до запуска детей; Git, данные, логи и `.run.lock`
принадлежат каждому клону. Ошибка одной территории не отменяет остальные.

Обычный `parse_and_push.sh` проверяет сеть и гейт дня, запускает `run_parse.py`
и публикует прочитанные данные с контекстом дайджеста. До 08:45 новости
накапливаются без рассылки. После открытия окна публикация доставки идёт
отдельной транзакцией: journal → `delivered_at` → marker-коммит с
`(Mac-парсинг)` → подтверждение marker SHA на remote. Это же сообщение
использует VPS. GitHub `replay_on_push.yml` собирает дайджест, отправляет
Telegram, публикует результат и отдельно запускает Web Push.

`cloud_run_ok.py --report` пропускает слот, когда сегодняшний день уже закрыт
по `delivered_at`. Качество чтения (`--run-complete`) влияет на диагностику,
но не разрешает раннюю доставку и не заменяет этот гейт. `--force` обходит
дневной гейт и окно времени, поэтому повторный ручной запуск может вызвать
новую рассылку.

После завершения всех парсеров `parse_all.sh` вызывает финальную доставку
`--deliver-pending`, затем на Mac последовательно обрабатывает импорты. Если
первая проверка была раньше 08:45, после импортов окно проверяется ещё раз.
С 13.09.2026 VPS задаёт `CM_IMPORTS_AFTER_PARSE=0`: импорт запускает отдельная
systemd-служба после завершения парсинга. Независимый `court-delivery.timer`
также использует общий `delivery_all.sh`. Расписание и зависимости служб —
в [VPS README](../vps-run/README.md).

`--deliver-pending` не обращается к судам и не запускает парсер. Он использует
общий lock, восстанавливает незавершённые транзакции, подтягивает Git и проверяет
`cloud_run_ok.py --can-deliver`: нужен свежий незакрытый выпуск завершённого
сегодняшнего прогона. День без новых событий тоже подходит; процент чтения
карточек отправку не запрещает. `--has-pending` отдельно отвечает только на
вопрос о наличии неотправленных новостей и не заменяет проверку готовности.

`delivery_all.sh` запускает доставку готовых выпусков по клонам параллельно,
без разнесения стартов и проб судов, с проверкой рабочего дня РФ. Имеющиеся
Mac LaunchAgents отдельный таймер для него не устанавливают. Занятый клон
пропускает попытку; на VPS следующую предоставляет таймер доставки.

> входит в локально подготовленный пакет, отсутствующий в `1a943a7f`.

> фактическое наличие функций проверяются в checkout своей территории;
> [состав среза](../../docs/Сверка_документации_2026-09-13.md).

## Настройки машины (вне репозитория)

Каталог `~/.config/court-monitor/`; секретные файлы — с правами `0600`.

| Файл | Зачем |
|---|---|
| `territories` | Пути к клонам по строке, `#` — комментарий. Можно выбрать другой список через `CM_TERRITORIES_FILE`. Пустой/отсутствующий список в общем helper возвращает `/Users/aleksandrselivanov/dashboard`; на VPS список обязателен. |
| `env.<регион>` | Настройки своего региона, например кэпы приёма. Без файла действуют дефолты кода; Actions Variables автоматически на машину не переносятся. |
| `telegram` | `token=…`, `chat_id=…` для shell-алертов. Это не разрешение Python-прогону рассылать дайджест. |
| `worker.<регион>` | `url=`, `owner_secret=`, `push_secret=` для своего Worker. Файл читается как данные, а не через `source`. Без него очередь не обрабатывается, остаётся импорт через `--file`. |
| `progress_token.<регион>` | Токен вех своего Worker. Общий `progress_token` остаётся fallback только для `hmao` и `sverdlovsk_yanao`; Башкортостану нужен собственный файл. |

Пример списка для трёх территорий — включать только согласованные для этой машины:

```
/Users/aleksandrselivanov/dashboard-ural
/Users/aleksandrselivanov/dashboard
/Users/aleksandrselivanov/dashboard-bashkortostan
```

Код региона: `hmao`, `sverdlovsk_yanao`, `bashkortostan`. Каждый форк получает
свои `REGION`, данные, Worker/KV, адреса и ключи. `git config merge.ours.driver true`
нужен для настроенных региональных merge-атрибутов, но не защищает новые файлы
и не заменяет аудит merge; подробности — [тиражирование регионов](../../docs/Тиражирование_регионы.md).

## Подготовка Mac-резерва

Используемый Python задаётся через `CM_PYTHON`, по умолчанию `/usr/bin/python3`.
Нужны зависимости [scripts/requirements.txt](../../scripts/requirements.txt),
`jq`, рабочий SSH-доступ Git через `ssh.github.com:443` и свои региональные
настройки. Установленные зависимости и ключи проверяются на самой машине.

Для маршрутов судов мимо VPN в сети Сбера:

```bash
cd /Users/aleksandrselivanov/dashboard
sudo cp ops/mac-local-run/court-monitor-route.sudoers /etc/sudoers.d/court-monitor-route
sudo chmod 440 /etc/sudoers.d/court-monitor-route
sudo visudo -c
```

Перед включением расписания Mac отключить таймеры VPS и убедиться, что службы
и дочерние процессы завершились. Остановка таймера не останавливает уже запущенную
службу. Два хоста одного региона не защищены общим lock и могут одновременно
писать данные или создавать доставочные коммиты. Процедура переключения —
[VPS README](../vps-run/README.md#откат-на-mac-если-vps-лёг).

После переключения исполнителя:

```bash
cp ops/mac-local-run/com.court-monitor.parse.plist ~/Library/LaunchAgents/
cp ops/mac-local-run/com.court-monitor.import.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/com.court-monitor.parse.plist
launchctl load ~/Library/LaunchAgents/com.court-monitor.import.plist
launchctl list | rg court-monitor
```

Парсинг: будни 06:00–08:30 каждые полчаса и 08:45 по местному UTC+5.
Импорт: будни 12/14/16/18/20. Последний слот парсинга и границу окна 08:45
менять согласованно. Для облачного исполнителя `crons` и `CRON_UTC` меняют
вместе с deploy; включать Worker-cron для перехода VPS → Mac не требуется.
GitHub replay остаётся каналом доставки обоих исполнителей. Секреты выбранного
LLM-провайдера, Telegram и Web Push проверяют в каждом репозитории отдельно.

На время жизни `parse_all.sh` `/usr/bin/caffeinate` блокирует idle sleep,
но не будит уже уснувшую машину; экран может погаснуть. LaunchAgent зависит
от пользовательской сессии. Пока он работает, следующий календарный слот
не встаёт в очередь. Финальная доставка страхует завершение парсинга после
08:45, но отдельного позднего таймера доставки в Mac plist нет.

### Параллельный режим и откат

| Переменная | Дефолт | Значение |
|---|---:|---|
| `CM_PARALLEL_TERRITORIES` | `1` | `0` запускает парсеры последовательно; финальная доставка сохраняется. |
| `CM_PARALLEL_STAGGER_SECONDS` | `600` | Интервал между стартами соседних территорий. |
| `CM_PARALLEL_FIRST_REGION` | `sverdlovsk_yanao` | Регион, переносимый в начало списка парсеров. |
| `CM_DELIVERY_WINDOW_MIN` | `525` | Граница 08:45 по местному времени. |
| `CM_IMPORTS_AFTER_PARSE` | `1` | Импорт внутри драйвера; VPS-обёртка принудительно задаёт `0`. |

Если общие маршруты не подготовлены, драйвер переходит к последовательному
обходу. `--check` всегда последовательный, без десятиминутной задержки.
Разовый полный запуск без параллельных парсеров:

```bash
CM_PARALLEL_TERRITORIES=0 bash ops/mac-local-run/parse_all.sh --anywhere
```

Для следующих Mac-слотов: `launchctl setenv CM_PARALLEL_TERRITORIES 0`;
вернуть штатно — `launchctl unsetenv CM_PARALLEL_TERRITORIES`.

## Проверки и ручные запуски

Эти команды имеют разные последствия:

```bash
# Читает локальную готовность; не обращается к судам и не публикует выпуск.
# Окно 08:45 и рабочий день сохраняются; свежесть remote не проверяется.
bash ops/mac-local-run/delivery_all.sh --check

# Сеть, маршруты, пробы реальных страниц; без парсинга и публикации данных.
# Записывает служебные логи/lock, может менять маршруты и передавать вехи.
bash ops/mac-local-run/parse_all.sh --check

# Читает настройки и очередь, проверяет доступность; пишет служебный лог/lock.
bash ops/mac-local-run/import_dumps.sh ~/dashboard-ural --check --anywhere
```

Успешная проба не доказывает чтение всех карточек. Сравнивать разрешённые
домены с текущим региональным реестром; несколько доменов могут иметь один IP.
HTTP 200 с капчей, защитой или заглушкой не считается успешным чтением дела.
`--anywhere` снимает требование офисной сети, но не обеспечивает доступ к судам.

```bash
# Полный запуск: данные, commit/push и возможная доставка после 08:45.
bash ops/mac-local-run/parse_all.sh --anywhere

# Реальная отдельная доставка готовых выпусков без парсинга.
bash ops/mac-local-run/delivery_all.sh

# Реальная обработка очереди выбранного клона.
bash ops/mac-local-run/import_dumps.sh ~/dashboard-ural --anywhere
```

Проверять результат отдельно: завершение парсинга → публикация данных →
принятый доставочный marker → успешный replay → опубликованный дайджест →
результаты Telegram/Web Push. Репозиторий и локальный `delivered_at` не
подтверждают все последующие шаги.

## Очередь операторских импортов на Mac

При `IMPORT_EXECUTOR="vps"` Worker сохраняет задания как `queued`, без
GitHub-dispatch. Основной обработчик — VPS: поллер новых отметок, регулярные
слоты и отдельная служба после парсинга. Mac читает ту же очередь при ручном
резервном запуске; внутри своего `parse_all.sh` он обрабатывает её после
всех парсеров. Рабочий `.run.lock` клона сериализует эти операции.

`import_dumps.sh` запрашивает `/admin/import-log?include_queue=1&logonly=1`:
полная `queue` сортируется по времени поступления и UUID. `items` — последние
50 записей истории и fallback для старого Worker, поэтому обновлённый
исполнитель требует обновлённого Worker каждой территории.

| Канал | Задание | Исполнитель |
|---|---|---|
| Дампы (`import:dump:`) | `GET /import-dump?key=` | `scripts/import_search_dump.py` |
| Точечные пачки (`import:case:`) | `GET /add-case-job?key=` | `scripts/add_cases_targeted.py` |

Дамп сохраняет выбранную инстанцию: `delo_id` (`5` — апелляция,
`2800001` — президиум) и `section` проходят из журнала через очередь,
CLI импортёра и итоговый отчёт. Это разные источники даже при одном домене.
Ссылки карточек должны относиться только к выбранному разделу: другой или
смешанный раздел отклоняется до чтения карточек и изменения картотеки.
У старых заданий без этих полей раздел определяется по самому дампу.

TTL обоих тел — 72 часа (`DUMP_TTL=259200`, соответствует `IMPORT_DUMP_TTL`
Worker). `queued` берётся сразу, без грейса. Повторы сетевых отказов и
частичного результата выбирает `import_queue.jq`; терминальная ошибка
«повтор не поможет — вставьте выдачу заново» исключает задание. Для аварийного
GitHub-пути сохранены грейсы живого задания: дамп 15 минут, пачка 50 минут.
Пачка повторяется целиком, чтобы отчёт сохранял итог по всем строкам. Успешные
результаты отсекаются по журналу Worker; дедуп и дочитка сохраняются.

Пометки «лист не нужен» (`writ_waiver`) очередь не исполняет: они не требуют
запросов к судам. При пустой очереди исполнитель выходит до проб судов.
`CM_IMPORT_SOURCE=vps` задаёт VPS-обёртка; без него отчёт и коммит подписываются
как Mac. Общий формат сводки — `ops/import_result_body.jq`.

```bash
# Пробный импорт без сохранения новых дел, отчёта оператору и commit/push.
# Обёртка всё же обращается к сети, готовит маршруты и делает git pull --rebase --autostash.
bash ops/mac-local-run/import_dumps.sh ~/dashboard-ural --dry-run --anywhere

# Настоящий импорт локального дампа (например, после истечения TTL в KV).
bash ops/mac-local-run/import_dumps.sh ~/dashboard-ural \
  --file ~/Downloads/выдача.html --court leninskiy--svd.sudrf.ru

# Для президиума можно явно закрепить инстанцию, как в задании из админки.
bash ops/mac-local-run/import_dumps.sh ~/dashboard \
  --file ~/Downloads/президиум.html --court oblsud--hmao.sudrf.ru \
  --delo-id 2800001 --section cassation
```

Пример `worker.sverdlovsk_yanao` (значения секретов вне Git):

```
url=https://api-ural.delosud.ru
owner_secret=…
push_secret=…
```

## Сеть, ограничения и живой лог

Полный launcher ставит `FETCH_MAX_RETRIES=3`, но сетевой слой повторяет только
разрешённые быстрые ошибки. ReadTimeout, connect-timeout, 4xx, капча и заглушка
не получают автоматические дополнительные попытки только из-за этого потолка.
Полный прогон использует `CARD_BREAKER_MODE=time`; импорт сохраняет короткий
`count`-профиль 5/3. Их параметры не переносить друг в друга без проверки.

Preflight обращается к реальным поискам кассации, апелляционных судов,
первой инстанции и известной карточке. Таймауты по умолчанию — connect 10 с,
read 65 с. Полный парсер имеет бюджет `RUN_DEADLINE_SECONDS=3300`: после
55 минут новые HTTP не начинаются, прочитанное сохраняется с результатом
`deadline_reached`. При неудачной half-open пробе хост не пробуется снова
в той же фазе. Полное описание — [сбор данных и парсеры](../../docs/technical/04-сбор-данных-и-парсеры.md).

`progress_pusher.py` фильтрует вехи из лога и отправляет батчи на
`POST /run-progress` своего Worker примерно раз в 60 секунд, а также при
финале или заполнении батча. Карточка «Ход последнего прогона» удалена
из админки 01.09.2026; статус даёт плитка «Последний прогон». Канал в KV
сохранён и читается через `GET /admin/run-progress` с авторизацией владельца или оператора.
URL берётся из `worker.<регион>`; старый адрес ХМАО используется только для
`hmao`. Башкортостан без своего Worker или токена вехи не отправляет.
`progress_pusher.py --check` проверяет адрес и наличие файла токена, но не
авторизацию на Worker. Парсинг продолжится и при отказе этого канала.

Токен из `progress_token.<регион>` должен соответствовать `PROGRESS_SECRET`
нужного Worker. Значения секретов, токенов и конфигов в Git не включаются.

## Логи и восстановление

- `parse_and_push.log`, `import_dumps.log` — логи своего клона, ротация по дням;
  `launchd.out.log` / `launchd.err.log` — вывод Mac-драйвера.
- `.runtime/parse_telemetry.json` — все попытки текущего дня, текущая фаза,
  transport/semantic исходы и breaker; `daily.planned_case_ids_today` и
  `daily.read_case_ids_today` хранят ID `домен|номер` по трём инстанциям.
  При новой дате история начинается заново. Непрочитанные карточки остаются
  в полном запланированном знаменателе.
- `.runtime/network_fingerprint.json` — VPN, маршруты, выход и результаты
  проб поиска/карточки. Полных HTML и URL карточек в telemetry нет; могут
  быть номер дела, домен и диагностический IP из страницы защиты.
- `.runtime/parse_txn.json` и `.runtime/delivery_txn.json` — незавершённые
  транзакции. При неизвестном исходе не удалять journal и `delivered_at`
  вручную: сначала установить состояние remote, иначе возможна потеря или
  повтор доставки. Следующий штатный запуск выполняет восстановление.

Runtime-файлы игнорируются Git и записываются атомарно. Прерванная попытка
telemetry при следующем старте помечается `interrupted`. Порог качества
чтения и итог доставки проверять отдельно.

## Усыпить резерв или удалить Mac-автоматику

Чтобы прекратить будущие Mac-слоты, выгрузить оба LaunchAgent:

```bash
launchctl unload ~/Library/LaunchAgents/com.court-monitor.parse.plist
launchctl unload ~/Library/LaunchAgents/com.court-monitor.import.plist
launchctl list | rg court-monitor
```

Перед передачей работы VPS проверить отсутствие активных дочерних парсеров
и импортов. Само наличие файлов plist на диске не означает работу агентов.
Для полного удаления Mac-автоматики после выгрузки можно удалить оба
установленных plist и `/etc/sudoers.d/court-monitor-route`. Это не требует
включать Worker-cron: основной исполнитель определяется отдельно.
