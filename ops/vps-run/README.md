# VPS-звено (боевой парсинг с 28.08.2026)

VPS — основной исполнитель парсинга и операторских импортов; Mac остаётся
резервом. Целевой сервер установки — Cloud.ru, `195.19.66.234`, Ubuntu 24.04,
часовой пояс `Asia/Yekaterinburg` (UTC+5).

Схема ниже сверена с файлами репозитория 13.09.2026. Это не проверка текущих
служб сервера, секретов, egress или доступности судов. Подключение третьего
клона, Башкортостана, зафиксировано в [датированном отчёте внедрения](../../docs/regions/Башкортостан_внедрение_2026-09-11.md);
первый плановый утренний цикл после подключения там отмечен как предстоящий.

**С 08.09.2026 очередь импортов — ОСНОВНОЙ исполнитель дампов и точечных
пачек** (решение юриста): Worker с `IMPORT_EXECUTOR = "vps"` в GitHub не
диспатчит, записи поступают в общую очередь `queued`. С 20.09.2026 она
обслуживается каждый день, включая выходные и праздники, во всех четырёх
территориях. Правило одинаково для дампов и одиночных добавлений/пачек дел.
**С 09.09.2026 — попытка по новой отметке**: таймер
`court-import-poll.timer` (круглосуточно каждые 5 минут) гоняет
`import_poll.sh` — один GET `/import-pending` на территорию (KV get, не list),
при новой отметке сразу `import_dumps.sh <клон> --anywhere`; занятый
`.run.lock` (утренний парсинг/слот) = пропуск тика без отметки. Слоты 12–20 —
ежедневная страховка для провалов: каждый час с 12:00 до 20:00 (с 22.09.2026)
по Екатеринбургу. Есть и утренний запуск очереди после парсинга. Поллер
проверяет новые отправки; неудачная попытка повторяется в страховочный слот,
а не бесконечно каждые пять минут. При занятом регионе первая попытка
ждёт освобождения `.run.lock`. Пустая очередь не вызывает запросов к судам.
Слоты
продублированы в `IMPORT_SLOTS_LOCAL` wrangler.toml — админка обещает
оператору именно эти часы; менять только парой (страж
`test_slots_var_mirrors_timer`). `vps_env.sh` экспортирует
`CM_IMPORT_SOURCE=vps` — им подписаны отчёт в журнал («🖥 обработано
сервером»), коммиты «(VPS)» и тексты ошибок.

**Очередь с 12.09.2026:** `import_dumps.sh` запрашивает
`/admin/import-log?include_queue=1&logonly=1` и обрабатывает полную `queue`
по порядку поступления. Последние 50 записей `items` остаются только историей;
старый формат поддержан на время выпуска. Сначала обновить Worker каждой
территории, затем скрипты исполнителя — иначе старая выдача ещё ограничена 50
записями. Блокировка `.run.lock`, условия повторов и расписания сохранены.

**С 13.09.2026 утренний обход, импорт и доставка работают отдельно.**
`court-parse.service` больше не ждёт очередь импортов: после завершения
(включая ошибку парсера) systemd запускает `court-import.service` через
`OnSuccess` / `OnFailure`. На VPS `CM_IMPORTS_AFTER_PARSE=0`; Mac-резерв
сохраняет импорт внутри общего драйвера. Слоты парсинга, порядок территорий
и интервал между их стартами не меняются. Занятый импортом клон пропустит
свою попытку парсинга, но общий утренний сервис не ждёт окончания импортов.

`court-delivery.timer` отдельно проверяет готовые выпуски по будням каждые
5 минут с 08:45 до 09:55, затем каждые 15 минут с 10:00 до 23:45 — только для
оставшихся незакрытых выпусков. Закрытый день без незавершённых транзакций
отсекается локально, без Git-запросов. Поздние тики также страхуют совпавшие
запросы запуска уже активной службы доставки. Общий календарь РФ отсекает нерабочие дни.
`delivery_all.sh` вызывает существующий `parse_and_push.sh --deliver-pending`
по всем клонам без интервала старта. Общий `.run.lock`, восстановление
транзакций, публикация данных и дневной гейт сохраняются. Готовность проверяет
`cloud_run_ok.py --can-deliver`: свежий незакрытый выпуск завершённого
сегодняшнего прогона. День без новых событий тоже подходит; процент чтения
не ограничивает отправку накопленного. Занятый клон ждёт следующего тика.
Служба ограничена `TimeoutStartSec=4min` и `TimeoutStopSec=30s`: зависший Git
не удерживает её бесконечно; следующий тик использует штатное восстановление
транзакции. После долгого импорта отдельная доставка
запрашивается снова, в том числе после 10:00: у слотов — зависимости службы,
у поллера — неблокирующий запрос только после фактического запуска очереди.
Пустой успешный тик поллера дополнительную доставку не запускает.

**Обёртки используют общую реализацию.** `parse_all.sh`, `import_all.sh` и
`delivery_all.sh` готовят Linux-окружение (`vps_env.sh`) и вызывают скрипты
из `ops/mac-local-run/` с `--anywhere`. Транзакции, гейт дня и обработка
очереди общие; расписание и способ запуска импортов/доставки различаются
между systemd VPS и LaunchAgents Mac. `CM_COURT_ROUTES_READY=1` отключает
офисные маршруты на VPS, `shims/netstat` закрывает macOS-специфику.
Доступность судов решают реальные HTTP-пробы, а не этот флаг.

Список `territories` задаёт участвующие клоны. Урал переносится в начало
списка парсеров; по умолчанию остальные стартуют в порядке списка с интервалом
600 секунд (`CM_PARALLEL_STAGGER_SECONDS`). `CM_PARALLEL_START_DELAYS` позволяет
задать задержки отдельных регионов в секундах от начала общего слота.
Остальные регионы сохраняют задержку по порядку списка; одинаковые значения
означают совместный старт. Некорректные и повторные записи останавливают драйвер
до запуска парсеров.

Согласованная настройка VPS с 20.09.2026 находится в
[60-region-starts.conf](systemd/court-parse.service.d/60-region-starts.conf):

| Территория | Задержка каждого слота | Первый старт, UTC+5 |
|---|---|---|
| Урал | 0 минут | 06:00 |
| ХМАО | 5 минут | 06:05 |
| Башкортостан | 10 минут | 06:10 |
| Тюменская область | 10 минут | 06:10 |

Для применения после обновления драйвера скопировать файл в
`/etc/systemd/system/court-parse.service.d/60-region-starts.conf` и выполнить
`systemctl daemon-reload`. Он дополняет прежний `50-stagger-trial.conf`;
таймеры парсинга, импорта и доставки не меняются. На Mac настройка сама
не включается. Первый автоматический цикл четырёх территорий с этой
настройкой на момент изменения ещё не выполнен.

Импорты в `import_all.sh`
обходят клоны последовательно; отдельная служба освобождает утренний драйвер,
но не отменяет общий `.run.lock` внутри каждого клона.

## Установка и обновление

1. `timedatectl set-timezone Asia/Yekaterinburg` — окно 08:45 и календарь
   выходных живут по местному времени (`vps_env.sh` жёстко проверяет +0500).
2. `apt install -y python3-requests jq`; `vps_env.sh` проверяет `requests`
   у `/usr/bin/python3`. Если выбран `CM_PYTHON`, зависимости должны быть и
   в этом интерпретаторе. `net-tools` для обхода через shim не требуется.
3. Клоны: `/opt/court-monitor/dashboard`, `/opt/court-monitor/dashboard-ural`
   и `/opt/court-monitor/dashboard-bashkortostan`. У каждого свои данные,
   регион и remote. Для форков настроить `git config merge.ours.driver true`,
   затем проверять результат каждого merge, включая новые файлы. Одного
   merge-driver недостаточно для региональной изоляции.
4. Отдельный deploy-ключ с правом записи для каждого репозитория.
   `~/.ssh/config` выбирает ключ по cwd Git-процесса: общий транспорт идёт
   через `ssh.github.com:443`. Пример настройки (имена файлов ключей
   сверить с установленными на сервере):
   ```
   Match host ssh.github.com exec "test $(pwd) = /opt/court-monitor/dashboard"
     IdentityFile ~/.ssh/deploy_hmao
     IdentitiesOnly yes
   Match host ssh.github.com exec "test $(pwd) = /opt/court-monitor/dashboard-ural"
     IdentityFile ~/.ssh/deploy_ural
     IdentitiesOnly yes
   Match host ssh.github.com exec "test $(pwd) = /opt/court-monitor/dashboard-bashkortostan"
     IdentityFile ~/.ssh/deploy_bashkortostan
     IdentitiesOnly yes
   ```
   known_hosts засеять: `ssh-keyscan -p 443 ssh.github.com`.
5. `~/.config/court-monitor/`: `territories` с путями участвующих клонов
   (например, Урал → ХМАО → Башкортостан), `env.<регион>`, `telegram`,
   `worker.<регион>` и `progress_token.<регион>` с правами `0600` для секретов.
   Коды регионов: `hmao`, `sverdlovsk_yanao`, `bashkortostan`. Общий
   `progress_token` совместим только с ХМАО/Уралом; Башкортостану нужен свой.
   Токены доставки в `env.*` не класть: Python не должен отправлять второй
   дайджест или Web Push. `worker.*` читается как данные, а не через `source`.
   Полная схема файлов — [в общих настройках](../mac-local-run/README.md#настройки-машины-вне-репозитория).
6. `cp ops/vps-run/systemd/court-*.{service,timer} /etc/systemd/system/`
   → `systemctl daemon-reload` → `systemctl enable --now court-parse.timer
   court-import.timer court-import-poll.timer court-delivery.timer`.

При обновлении этой схемы нужны новые общие helpers во всех клонах:
`cloud_run_ok.py` и `parse_and_push.sh` читаются из собственного клона
региона. После обновления кода скопировать изменённые service/timer,
выполнить `systemctl daemon-reload`, затем `systemctl enable --now
court-delivery.timer`. Проверить `systemctl cat court-parse.service
court-import.service court-import-poll.service court-delivery.service` и
`systemctl list-timers court-delivery.timer`. Саму службу доставки вручную
для проверки не запускать: она действительно публикует выпуск.

**Обновление слотов:** после обновления кода скопировать изменённые unit-файлы,
выполнить `systemctl daemon-reload`, перезапустить изменённые таймеры и
проверить `systemctl list-timers`. Например, для импортных слотов —
`systemctl restart court-import.timer`. При изменении этих часов сохранить
соответствие `IMPORT_SLOTS_LOCAL` в Worker каждой территории и отдельно
проверить его публикацию. Установка таймера в репозитории не обновляет systemd.

## Наблюдение

- `journalctl -u court-parse -u court-import -u court-import-poll -u court-delivery --since today`
  (поллер при пустом флаге не запускает обработку очереди)
- логи прогона: `<клон>/ops/mac-local-run/parse_and_push*.log`,
  `import_dumps*.log` (ротация по дням, как на Mac)
- вехи в KV Worker — через свой `worker.<регион>` и `progress_token.<регион>`;
  чтение через `GET /admin/run-progress` с авторизацией владельца или оператора. Карточки
  живого лога в текущей админке нет, статус даёт плитка «Последний прогон»
- Telegram-алерты подписаны «Mac-парсинг (<клон>)» — префикс жёсткий в
  боевом скрипте, менять только вместе с ним (не дублировать).

Проверка без отправки выпуска из нужного клона:

```bash
bash ops/vps-run/delivery_all.sh --check
```

Она проверяет только локальную готовность и календарь, без судов и Git;
до 08:45 завершится на закрытом окне. Успех команды не подтверждает
публикацию данных или рабочую авторизацию. Действительную цепочку проверяют
по журналам: завершённый прогон → данные на remote → доставочный marker →
GitHub replay → Pages и результаты Telegram/Web Push. `delivered_at` и
принятый marker сами по себе не доказывают завершение всех внешних шагов.

## Откат на Mac (если VPS лёг)

1. VPS: `systemctl disable --now court-parse.timer court-import.timer
   court-import-poll.timer court-delivery.timer`
   Затем убедиться через `systemctl is-active`, что `court-parse.service`,
   `court-import.service`, `court-import-poll.service` и `court-delivery.service`
   завершились: отключение таймера не останавливает уже работающую службу.
   При недоступном сервере нужно подтвердить его остановку до запуска Mac.
2. Mac: `launchctl load ~/Library/LaunchAgents/com.court-monitor.parse.plist`
   и `launchctl load ~/Library/LaunchAgents/com.court-monitor.import.plist`.
   Перед загрузкой проверить локальный список территорий: подготовленный клон
   Башкортостана сам по себе в него не добавляется.

Разовый резервный запуск также выполняется через «СберСуд-пульт.command»
после проверки отсутствия другого писателя. `--force` обходит дневной гейт
и окно 08:45 и может создать повторную рассылку.

## Острые углы

- Одновременно VPS и Mac работать НЕ должны: гейт «один дайджест в день»
  смотрит только `delivered_at` (после git pull) и от гонки двух хостов в
  одном окне не защищает; черновые пуши двух писателей конфликтуют.
- Обновление исполнителя не требует менять nginx-шлюзы `api2-*.delosud.ru`.
  Тариф и ресурсы сервера проверяются в панели провайдера отдельно; старые
  оценки стоимости и памяти не доказывают текущие условия.
- ssh-канал Mac→VPS иногда рвётся («closed by remote host») — на прогоны
  не влияет (systemd), только на ручное наблюдение.
